# 人手採点を候補手評価へ戻す — P0（棋譜外へ一般化するかの判定）

2026-08-26。issue #24 の P0。**この文書は P0 の記録**で、P1（bounded residual の
runtime 統合）へ進むかどうかの判断を「判定」節に書く。

## 位置づけ（変えないこと）

- P0 の目的は二択を決めること: ①棋譜外へ一般化する信号がある → 小さな残差モデルを
  P1 で統合する ②同一棋譜の暗記しかできない → **実装せず**、必要な追加レビュー数と
  局面層を確定する
- scenario suite を arena の代わりにしない。**最終採否は通常 arena のガントレット**
- `value_nn`（勝敗教師）を置き換えない。人手の局所順位教師とは役割が違う
- 未採点候補を悪手として扱わない（`?` は欠測）
- 真実盤面・実戦の正解手・コメント文・棋譜名を実対局の特徴量に入れない

## 実装

| 部品 | 場所 | 役割 |
| --- | --- | --- |
| eval → 決定点の復元 | `src/eval_rank.rs` | `## N手目` → `ply = N-1`、`### N手目（和名(USI)の反則後）` → 同じ ply ＋ 元棋譜の `*illegal` をその USI まで注入。元 KIF は `scenarios/archive/<eval名>.kif`（無ければ `scenarios/<eval名>.kif`） |
| 特徴量 | `eval_rank::feature_row` | 入力は `PlayerView` と `CandidateScore` **だけ**。46列（内訳・候補集合内の位置・状態・着手） |
| エクスポータ | `bin/export_eval_rank_data` | 決定状態 × seed で `choose` → 候補ランキングと採点を結合して CSV ＋ summary JSON |
| 分析 | `scripts/eval_rank/fit_residual.py` | leave-one-source-KIF-out ＋ 訓練 fold 内の nested CV（α）。pairwise ridge |

### 復元の関門（黙って落とさない）

- 復元した `(ply, fouls)` に対応するシナリオ kif があれば `scores=` の**完全一致**を
  検査し、ずれたら停止する。反則後ブロックの対応が `foul_blocks.py` の FOUL_MAP と
  一致することも `cargo test 反則後ブロックの対応がpython側の表と一致する` が検査する
  （別の手目・別の反則後サブ状態へ接続する事故は PR #3 で実際に起きた）
- **採点済みなのに現行候補集合に無い手**は `in_candidates=0` の行として残す。
  黙って落とすと候補生成 recall が測れず、「未採点候補の除外による見かけの改善」と
  同じ穴が分析側に開く
- 現行候補にあるが eval に未収載の手、ランキングが取れなかった決定状態も summary に件数で出る

### 特徴量の健全性

`feature_row` の入力は自分側の完全既知情報（`PlayerView`）と bot 自身が計算した
内訳（`CandidateScore`）だけで、`Position`（真実）は型として渡らない。
`cargo test 特徴量は相手の駒配置に依存しない` が「相手の駒を全部消した別の真実」から
作った view で行が変わらないことを実測で確かめる。
タイブレーク乱数は `CandidateScore::tiebreak` へ分離したので、特徴量に載る `adjust` は
乱数を除いた決定的な補正だけ。USI 文字列・絶対マスの one-hot・棋譜名・ply の固有 ID は
そもそも列に無い。

### 分割（ここを間違えると全部無意味になる）

採点 5,035 件のうち **94.4% が `quest_20260731` と `quest_0809` の2局由来**なので、
行・候補・決定点のランダム分割はほぼ確実にリークする。分割単位は元 KIF だけにし、
同じ棋譜の通常ブロック・反則後ブロック・全 seed を必ず同じ fold へ置く。
主評価は leave-one-source-KIF-out、α は訓練 fold 内の nested CV（これも元 KIF 単位）。
指標は source KIF ごとの macro 平均で、行の micro 平均は主張に使わない。
seed は独立標本として数えない（決定状態ごとに平均してから状態を平均する）。


思考予算 2000ms（既定）・seed 0..3。決定状態 272（うち 180 は対応シナリオがあり
`scores=` の完全一致を確認）、採点 5,035 件・未採点 27 件、候補行 123,816。

### 指標の作り方（PR #25 の5回のレビュー反映）

初版から5回直している。**8件とも「残差ランカーが良く見える」側へ効いていた**ので、
同種の判定をやり直すときは先にここを読むこと。

- **未採点の top-1 を仮の点で埋めない**。`?` は欠測という契約どおり、得点系は
  「top-1 が採点済みの決定状態」だけで条件つきに数え、「未採点手を選んだ率」を
  別指標にする。仮 4 点で混ぜると、未採点選択が増える側の腕の得点が実点次第で反転する
- 条件つきの平均は腕ごとに母集団が変わるので、**合否も CI も「両腕とも top-1 が
  採点済み」の決定状態だけの対比較**（`paired_metrics`）で出す
- **未採点への逃避が増えたら判定を止める**（許容 +0.01）。**macro だけでなく
  大きい quest 1局ごとにも見る**: macro の関門だけだと、その局で逃避が増えても
  他クラスタで減れば相殺されて通る（実測でも macro +0.125 に対し
  quest_0809 は +0.366・quest_20260731 は +0.348 と、局ごとに見ると3倍近い）
- **タイブレーク乱数はどの特徴量にも載せない**。`adjust` だけでなく `score` /
  `static_score` も乱数を含むので3つとも引く。順位系は `det_order`（乱数を除いた
  スコア）で付け直し、**完全同点は USI の辞書順で割る**（安定ソートに任せると
  乱数の並び順がそのまま `rank` / `rank_frac` に残る。実測で決定的スコアが完全同点の
  候補は 8,145 件、1,088 決定状態×seed のうち 706 = 65% に存在した）
- **P1 の統合形は順位番号でなく実スコアへ合成する**。乱数込みの実スコアを
  非特徴列 `engine_score` として出し、baseline の再現と
  P1 の gain 側合成（下記）の数値ベースに使う。順位番号
  （`engine_rank`）へ残差を足すと候補間の実スコア差が消え、同じ残差でも順位差だけで
  逆転可否が決まる別物になる。`engine_rank` は現行順位の監査用として残す
- **`engine_score` を丸めない**。`{:.6}` で出すと 5.0000004 と 5.0000003 が同値になり、
  現行方策では順位がついている候補が CSV 上で同点になる（実測で
  **1,088 決定状態×seed のうち 19 件**が該当した）。Rust の既定表示（round-trip する
  最短表現）で出し、読み込み時に「`engine_score` の降順が `engine_rank` の昇順と
  厳密に一致する」ことを検査して、崩れたら停止する
- **P1 の統合形は `gain` 側へ足す**。issue #24 の設計は
  `gain' = gain + 残差` → `combine_score(gain', p_legal, foul_cost) + 既存の外側補正` で、
  「学習値が合法性を外側から迂回しない」ための明示的な制約。最終 score へ直接
  足すのとは**等価でない**（`combine_score` は正の gain を `p_legal` で割り引く
  非線形式）。例: gain=2 / p_legal=0.5 / foul_cost=0 / 残差=1 なら、現行 1.0・
  P1 案 1.5・外側加算 2.0。実装は差分だけを `engine_score` へ乗せる
  （`p1_composed`）。実測でも W=4 の未採点率が 0.067 → 0.029、macro top-1 が
  5.959 → 6.322 と変わったので、差は無視できない
- **合否に使う量はすべて replicate（別エクスポート）平均で出す**
  （`MIN_REPLICATES=3`）。1本で `d_conc >= 0.05` を合格にすると、壁時計予算由来の
  ノイズだけで P0 合格を出せる。本数が足りない実行では concordance を「判定不能」と
  し、**合格を出さない**。得点系も1本目だけで決めると**引数の順序で判定が変わる**
  ので、大きい quest の得点・局ごとの未採点率・小さい eval の最悪差・fold 間の
  符号まで全部平均する
- **replicate は「同じ実験の独立サンプル」だけを数える**。列名とクラスタ名しか
  見ないと、同じファイルを3回渡すだけで本数関門を通せてしまう。
  ①中身の hash が相異なること ②`(decision_state, seed, usi, 採点, 候補内か)` の
  母集団が一致すること（**候補外の手も USI ごと**。点数の multiset だけだと別の手へ
  入れ替わっても通る）③summary JSON の `budget_ms` / `config_fingerprint` /
  **`source_fingerprint`** / **`data_fingerprint`** / `seeds` / **`jobs`** /
  `eval_fingerprint` が全 replicate で一致すること、を検査する。
  `jobs` は**実効並列度**（`--jobs` を unit 数で clamp した実際の worker 本数）:
  思考予算は壁時計なので、同じ 2000ms でも同時に走る unit 数で CPU contention が
  変わり、1本あたりの探索量と分布が系統的にずれる（PR #25 レビュー指摘 P1）。
  指紋は2つに分ける:
  - **`source_fingerprint`（コード版と実効ビルド条件）** = `build.rs` が
    **コンパイル時に**焼き込む `src/**/*.rs`（凍結版・共有モデル込み）＋
    `Cargo.lock` ＋ `Cargo.toml` ＋ `build.rs` 自身のハッシュに、
    **profile / target / opt-level / features / `RUSTFLAGS` / rustc 版**を混ぜたもの。
    - 実行時に worktree を読むと、commit A でビルドしたバイナリを worktree B の
      状態で走らせたときに **A の挙動を B の指紋で記録**してしまう（長い実行中の
      編集でも同じ TOCTOU）。**実測**: 再ビルドせずに worktree を編集しても指紋は
      動かず、再ビルドすると動き、元に戻すと戻る
    - ソースだけでは足りない。同じ head を debug と release でビルドすると
      **指紋が一致してしまう**が、思考予算が壁時計なので探索量と出力分布は
      桁で違う。ビルド条件を混ぜて分離した（**実測**: debug と release で
      焼き込み値の共通は 0 件、`RUSTFLAGS` を変えても変わる）
    - あわせて **exporter は release ビルドでないと起動時に止まる**。
      壁時計予算の計測を debug で取らせない
  - **`data_fingerprint`（実行時データ）** = 解決済みの定跡パス（`config.joseki_path`
    = `TSUITATE_JOSEKI`）の**中身**と、使った元 KIF の中身。`config_fingerprint` には
    定跡の**パス文字列しか入らない**ので、同じパスの中身を差し替えると実効挙動だけが
    変わる（**実測**: 中身を変えると `config_fingerprint` は不変のまま
    `data_fingerprint` だけが変わる）。
    **ディスクを読み直さない**のが要点: 元 KIF は `parse_kif` に渡した**その bytes**を
    そのまま指紋にする。長い実行の最後に読み直すと、A を読んで走った後に同じパスを
    B へ差し替えられたとき **CSV は A 由来なのに B の指紋が付く**。定跡は
    `opening.rs` が遅延ロードするので、開始時に読んだ bytes と実際に使われる bytes は
    **A→B→A の差し替えで食い違いうる**（開始・終了の比較では検出できない。
    PR #25 レビュー指摘 P1）。開始時の bytes を `opening::preload` で明示的に
    キャッシュへ入れ、**戦略も指紋も同じ immutable な bytes を見る**形にした
    （既にロード済みなら「どの定跡で走るか確定できない」として exit 2。
    実行中にディスク側が変わっても run は開始時の bytes で走っているので、
    告知だけして CSV は有効とする）

  summary の場所は CSV 名から一意に決まる（exporter の `--summary` は廃止し、
  `--out` は `.csv` 必須を起動時に検査する。`.csv` で終わらないと summary が
  CSV を上書きして、重いエクスポートの最後に結果が消えるため）
- **P1 合成の成分も丸めない**。`gain` / `p_legal` / `foul_cost` は特徴量であると
  同時に gain 側合成の入力なので、特徴量列も全精度で出す

### 測定そのもののノイズ（**concordance の門は 3 replicate でもまだ揺れる**）

思考予算が壁時計ベースなので、同じコード・同じ設定でもエクスポートのたびに粒子数が
揺れる。**同一コミットで3本取った replicate**（`--seeds 4` を3回。分析は
`fit_residual.py rep1.csv rep2.csv rep3.csv` で集約する）:

| 量 | #1 | #2 | #3 | 平均 |
|---|---:|---:|---:|---:|
| macro concordance の差 | +0.076 | +0.067 | +0.020 | **+0.054** |
| macro 未採点率の差 | +0.126 | +0.060 | +0.072 | +0.086 |
| 小さい eval 群の最悪 top-1 差 | −1.000 | −1.071 | −0.214 | −0.762 |
| quest_0809 の対比較 top-1 差 | −0.987 | −0.695 | −1.453 | **−1.045** |
| quest_20260731 の対比較 top-1 差 | −0.730 | −0.332 | −0.314 | **−0.458** |

**concordance は 3 本の平均でも安定しない**。指標の定義が同じ replicate 3本組を
2セット取ったところ、平均は **+0.022 と +0.054** で、門（+0.05）をまたいだ
（個々の値は −0.030 〜 +0.076）。**3 本は「1本で符号を論じる」よりましというだけで、
この量の合否を確定させるには足りない**。今回のセットではこの条件だけが「合」に
なったが、それは効果の証拠ではない。

一方**得点系は2セット・6本を通して安定して負**（大きい2局の対比較 top-1 は
−0.31〜−1.45、未採点への逃避は +0.28〜+0.38）。**P0 の判定はこちらで確定している。**

### 採点の被覆（**これが効き方を決めている**）

- 1決定状態あたりの候補 **113.8 手、うち採点済み 18.3 手（16.1%）**
- 現行 score の **top-1 が採点済み 94.1% / top-3 88.3% / top-10 76.5%**

### bounded residual（P1 の統合形）の W スイープ

issue #24 の P1 は **gain 側**へ足す形なので、そのとおりに合成する:

```
gain' = gain + W × cap × tanh((r − r̄) / cap)   (cap=2 点)
score' = combine_score(gain', p_legal, foul_cost) + 既存の外側補正
```

**W=0 は現行と完全一致**。得点は W=0 との対比較（1本目）。

| W | macro top-1 得点 W=0→W | macro 0〜2点 top-1 率 | quest_0809 の差 | quest_20260731 の差 | 未採点率 | concordance |
|---:|---|---|---:|---:|---:|---:|
| 0 | 6.116 → 6.116 | 0.289 → 0.289 | ±0 | ±0 | 0.021 | 0.739 |
| 0.1 | 6.116 → 6.083 | 0.289 → 0.279 | +0.140 | −0.045 | 0.020 | 0.746 |
| 0.25 | 6.118 → 6.098 | 0.289 → 0.275 | +0.067 | −0.048 | 0.019 | 0.750 |
| 0.5 | 6.119 → 6.151 | 0.289 → 0.270 | +0.056 | +0.016 | 0.020 | 0.753 |
| 1 | 6.118 → 6.240 | 0.289 → 0.260 | +0.033 | +0.087 | 0.019 | 0.763 |
| 2 | 6.114 → 6.199 | 0.288 → 0.264 | −0.037 | +0.074 | 0.023 | 0.784 |
| 4 | 6.122 → 6.233 | 0.289 → 0.257 | −0.132 | −0.119 | 0.026 | 0.812 |

**大きい2局は W ごとに符号を入れ替え、セットが変われば値も入れ替わる**
（前のセットでは W=4 が −0.201 / +0.018、今回は −0.132 / −0.119）。
concordance だけが W に単調（0.739 → 0.812）で、これは**全バージョン・全 replicate を
通して唯一一貫している所見** ——**順位は揃うが、指す手は良くならない**。

### 層別・seed・学習曲線

- 層別（holdout 予測のみ・条件つき）: 被王手・反則後の小さい eval 群で逆行が出る
- seed を変えたときの選択一致率は上がるが、**良い兆候ではない**: 残差ランカーは
  粒子由来の項への依存が薄いぶん決定が安定するだけで、安定して悪い手を選んでいる
- 学習曲線（訓練に使う元 KIF を 1..7 本に振る）: 標準偏差はどこでも ±0.16〜0.19 で、
  本数を増やしても縮まない。**分散が「どの棋譜を holdout にしたか」で決まっている**

### 学習された係数

大きいのは `static_gain` / `to_rank_own` / `static_score` / `dist_own_king`（負）/
`checker_removal`（負）/ `risk` / `is_drop`（負）/ `mover_value`（負）。
`score` 単体の係数よりそれ以外のノルムの方が1桁大きいので、**現行 score の再現では
ない**（暗記でもない: USI・絶対マスは列に無い）。向きは `bin/eval_features` の
局面内中心化回帰（玉候補距離1 +1.08 / 安さ +0.88 / 打ち −0.43）と一致する。
ただしこの一致は**選ぶ手の改善には変換されていない**。

## 判定

**P0 不合格。runtime 実装（P1）をしない。**

| 合格条件 | 実測（**replicate 3本の平均**） | 判定 |
|---|---|---|
| 大きい quest 2局の完全 holdout で top-1 得点 +0.5 以上 **または** 0〜2点 top-1 率 25% 以上の相対減 | 0809: **−1.05** / −92.5%、31: **−0.46** / −18.2%（対比較。2セット6本とも負） | 否 |
| macro pairwise concordance +5pt 以上 | **+0.054**（+0.020 / +0.067 / +0.076）。ただし別セットでは +0.022 で、**3本平均でも門をまたぐ** | （合だが**不安定**） |
| 被王手・反則後の小さい eval 群で top-1 −0.5 超の逆行がない | 最悪 **−0.76** | 否 |
| 改善が未採点候補の除外・特定USI/マスの暗記・1棋譜で説明されない | fold 間で concordance 差の符号が反転（+0.000 / −0.007 / −0.051 / +0.122 / −0.209 / +0.596 / −0.025 / +0.008） | 否 |
| 未採点への逃避が増えていない（許容 +0.01） | macro **+0.086**、局ごと **+0.333 / +0.343** | 未確定 |

中止条件のうち **「source-KIF holdout で改善が消える / 符号が局ごとに反転する」**と
**「top-1 得点は上がらず、順位一致だけが上がる」**に当たる。concordance の行は
このセットでは門を超えたが、**別セットでは +0.022 で超えない**ので効果の証拠にならず、
そもそも他の3条件が落ちているので判定は不合格で確定する。

**候補生成は律速ではない**（recall 99.7%）ので、issue が用意していた分岐
「candidate recall が低ければ次 issue を候補生成の多様化へ切り替える」は**該当しない**。

## 再判定に要るもの（issue の「追加4局」を具体化する）

方向自体（人手の局所順位に情報がある）は否定されていない —— concordance は W に
単調で、`bin/eval_features` の回帰と向きが一致する係数も出る。
再判定するなら、**先に3つ直す**。順番が逆だと同じ結果が出る。

1. **採点の被覆を、方策が到達しうる範囲まで広げる**（今回の主因）。
   候補 113.8 手のうち採点は 18.3 手（16.1%）で、現行 top-10 でも 76.5% しか
   採点されていない。順位を組み替える器を入れる以上、**その器が持ち上げる手が
   採点済みでなければ測れない**（残差ランカーの未採点選択は大きい2局で +0.35 前後）。
   既存の `append_unscored.py` ループ（候補ノブで suite → 2回以上選ばれた未収載手を
   `?` 追記 → 採点 → `sync_eval.py`）を、実験ごとでなく**学習ループの内側**へ
   入れる必要がある。概算コスト: 現行の被覆（上位15）を上位30へ広げるだけで
   1棋譜あたり +約9手/決定点 ×約100決定点 = **+900手の採点**
2. **独立棋譜を増やす**。採点の 94.4% が2局由来で、学習曲線の標準偏差は
   本数によらず ±0.16〜0.19。±0.05 の門をこの分散で判定できない。
   さらに macro 平均は1決定状態のクラスタと106状態のクラスタを同じ重みで扱うので、
   **小さい eval が増えるほど macro が実態から離れる**。追加は**既存2局の近傍でなく
   対人実戦から**、先後・序中終盤・被王手・反則後で層化して**4局以上、かつ全局
   レビュー**（1決定点だけの eval を増やしても macro を歪めるだけ）
3. **測定を複数エクスポートで平均する。ただし concordance は3本でも足りない**。
   3本組を2セット取ると平均が +0.022 と +0.054 で門（+0.05）をまたいだ。
   `fit_residual.py rep1.csv rep2.csv rep3.csv` が replicate として集約し、
   3本未満なら「判定不能」で合格を出さない（合否に使う量はすべて平均するので
   引数順にも依存しない）が、**この量を根拠に採否を決めるなら本数の再設計が要る**。
   得点系は6本とも同じ向きなので、判定はそちらでする

この3つが済むまで、人手採点は**目的関数（suite / SPSA）としてだけ使う**という
現状の役割を変えない。`bin/export_eval_rank_data` と `scripts/eval_rank/fit_residual.py`
は、採点が増えたときに同じ判定をやり直すための配管として残す（既定挙動は不変）。
