## 段階①②（opp_move NN・信念ネット）

**段階①（opp_move_weightのNN化）は本番統合済み**（estimator_v9、2026-07-22
凍結）。`src/opp_move_features.rs`（24特徴量の共有定義。学習エクスポートと
estimator推論の両方がここを参照）・`src/opp_move_nn.rs`（重み定数+手書き
forward pass。1手あたり最大10万回超のホットパスなのでONNX等は使わない）・
`bin/export_opp_move_data`（アリーナ記録→候補集合CSV）。学習は tsuitate-nn の
`train_opp_move.py`（候補集合内softmax条件付きNLL、`--feature-set base|piece`で
アブレーション）、重み書き出しは `export_opp_move_weights.py`。
再学習の手順: 記録用アリーナ（例 500局×3基準）→ artifact回収 →
`export_opp_move_data` → 学習（**4シードで頑健性確認**）→ export → cargo test
（numpyクロスチェックの期待値も再生成）→ `scenario suite`＋`kakutori diag` →
200局ガントレット。**定石（joseki.json）を更新したら学習データも再生成する
こと**（定石は実行時読み込みで凍結版＝教師側の序盤分布も変わる。①-bの
from_home等は序盤感度が高い）。NN出力のclamp(-15,15)は分布外入力への
安全弁なので外さない。
逆方向反則特徴量 my_foul_count_last_turn（24次元目、2026-07-23追加）は
現行のbot教師では寄与ゼロ（ゼロ化アブレーションでNLL差0.0002・
新1512局データの再学習も対v10互角400局）だが、人間対局データ等で
効く可能性を見て**当面残す**（ユーザー判断。「効かないから削る」提案は
しない）。同時に行った両NNの新データ再学習（opp_move seed0 /
value seed2）は強さ中立のままマージ済み（valueはオフライン較正が改善:
kakudo 正解シード1/4→3/4）。

## opp_move NN の学び直し（2026-10-30）

**なぜ**: 推定器の相手モデル（粒子を進めるときの相手の手の事前分布と、2手読み・`rl_search` の
応手予測）の教師は estimator 系の bot の 608局（2026-08-21）だけだった。方策ネット（`rl_*`）が
主役になってからは「方策が大きく変わったら教師を再生成する」の運用ルールに当たるのに、
止まっていた。`bin/opp_model_fit` で測ると方策ネットの手（とくに MMD の打ち）と人間の手を
一番当てない（`docs/diagnostics.md`）。rl_mmd_v4 の探索が効かない一因も、MMD どうしの対局で
粒子が相手の駒を見失うことだった（`docs/rl-deepnash-design.md` の「探索が MMD の版で伸びない理由」）。
人間の対局は `records/` の59局しか無いので、**bot の指し方を広く混ぜて学び、人間の対局は
検証にだけ使う**（ユーザーと決めた方針）。温度で平らにするだけでは直らないことは先に確かめてある
（`docs/knobs.md` の `TSUITATE_OPP_MOVE_TEMP`）。

**教師**: `cargo build --release --bin arena && scripts/opp_move/gen_teacher.sh <出力>` で
arena を手元で回す。候補4体（rl_mmd_v4 / rl_deduce_v10 / rl_v25 / rl_guard_v1）× 基準
13系統（rl_mmd_v4 / rl_mmd_v3 / rl_mmdv3branch_v1 / rl_deduce_v10 / rl_deduce_v7 /
rl_selfplay_v4 / rl_v30 / rl_v25 / rl_v22 / rl_speed_v3 / rl_speed_v4 / rl_guard_v1 /
rl_nyugyoku_v2）× 40局 = 系統ごとに160局。estimator_v14 も候補4体と40局ずつで160局、
計2240局。arena の記録は候補側の視点なので、`export_opp_move_data` が書き出すのは基準側の手
（= 系統ごとに分けられる）。`cargo build --release --bin export_opp_move_data &&
python3 scripts/opp_move/export_by_style.py train.csv <出力>/pol_* <出力>/est_*` で
`style` 列つきの1つの CSV（234万行・候補手単位）にまとめる。所要は4コアで方策ネットどうしが
約1時間、estimator_v14 が約30分。

**学習**: tsuitate-nn の `python3 train_opp_move_weighted.py --data train.csv
--out ../tsuitate-bot/src/opp_move_nn.rs --weight estimator_v14=13 --seed 3`。
構造は従来どおり 26→16→1・候補集合内 softmax の NLL・対局単位で15%を検証に回して早期打ち切り。
`--weight estimator_v14=13` は estimator_v14 の決定点を13回数える = **方策ネット13系統の合計と
estimator_v14 が半々**。続けて `python3 scripts/opp_move_crosscheck.py ../tsuitate-bot/src/opp_move_nn.rs`
で numpy クロスチェックの期待値を出し直し、`cargo test`。凍結版は固定コピー（`opp_move_nn_v25.rs`）を
使うので動かない（`SHARED_MODEL_PINS` も `opp_move_nn.rs` を pin していない）。

**検証（オフライン）**: 学習に使っていない別の対局で、正解手の平均 log p
（観測と整合する候補集合の中の softmax。tsuitate-nn の `scripts/opp_move_eval.py`）:

| 方策ネットの自己対局 180局（rl_mmd_v4 / rl_deduce_v10 / rl_v25 各60局） | −2.85 | −2.06 | **−2.32** | −2.14 | −2.54 | −2.25 |

- 方策ネットだけで学ぶ（重みなし）と方策ネットはよく当たるが、estimator_v14 と人間が旧より悪くなる。
  **人間の手は bot の指し方の幅の中にあって、両方の型を混ぜたものが一番当たる**（確率の半々の混合が
  人間で一番良い）。混合を推論で持つと候補集合ごとに2つの正規化定数が要ってホットパスが変わるので、
  1つの MLP に近似させた。データの重みで半々にする ×13 が人間の前半30局で一番良く、ホールドアウトの
  後半29局でも旧より当たる（1位率 30.0 → 31.6%）
- ×13 でも **2026-07 の estimator の bot の手は当てにくくなる**（−3.14 → −3.39）。estimator_v14 の手は
  保つ（−2.75 → −2.78）ので、古い estimator の指し方が v14 と違い、旧モデルの得意分野だったということ
- seed による揺れは小さい（×13 の seed 0〜3）: 方策ネットの自己対局 −2.29〜−2.35、estimator_v14 −2.75〜−2.81、
  人間の後半29局 −3.32〜−3.39（どれも旧の −3.44 より良い）、2026-07 の bot −3.31〜−3.46。
  人間の前半30局で一番良かった seed 3 を採った
- 隠れ層を 16 → 32 に広げても（×13・seed 3）両方の型は同時に当たらない: 方策ネットの自己対局 −2.30・estimator_v14 −2.78 は
  同じで、人間の後半29局 −3.39・2026-07 の bot −3.50 とむしろ悪い。ホットパスの計算も倍になるので 16 のまま

**実戦での効き（手元、旧と同じ局・同じ決定点で対にした比較）**:

**判断**: 新しい重みのまま進める（e03dc6a）。本番の `rl_search:rl_v25` の相手は人間で、人間の手への当てはまり
（ホールドアウト −3.44 → −3.33）と人間相手の粒子（一様事前からの上積み +0.113 → +0.140）が良くなり、アリーナは勝率中立で
反則が全部の対で減り、suite も全体では中立だから。残る後退は2つ: **王手中に離れた駒からの王手を説明しにくくなった**
（kakutori・arena-check-foul03）のと、**2026-07 の estimator の bot の手を当てにくくなった**（人間側から見た粒子が悪化。
今の対局相手には居ない指し方）。前者の次の手は、王手を掛ける手だけ教師の重みを変える（estimator 系の局の王手の手を厚くする）か、
CheckSolver 側で粒子の投票の重みを下げるか。戻すなら `git revert e03dc6a`（凍結版は固定コピーなので動かない）

## 段階③ valueネット: フェーズ2で本番統合済み（estimator_v10）

**フェーズ2（2026-07-22〜23、estimator_v10 凍結）で `strategy.rs::evaluate()` へ
統合済み**。粒子ごとに (state16+transition6) → 勝率相当[0,1] を
`src/value_nn.rs`（手書きforward pass 22→64→32→1、約0.6µs/回）で推論し、
重み付き平均の中心化値を `value_nn_w`（既定6.0、SPSA対応、
`TSUITATE_VALUE_NN_W` で上書き可＝切り戻しノブ。凍結版は反応しない）で
歩価値スケール化して gain 内（= combine_score の p_legal 割引の内側）へ加算。
設計上の要点:
- **王手中（you_in_check）はNN項無効**。w=6 で王手回避プローブの反則試行が
  増え dragon-check-drop で反則負け2/20が出た実測への対応。王手回避は
  CheckSolver（制約推論）の領分
- **重みは w 選定スイープで決める**（w=3 では gold-check の悪手 17/20 を
  変えられず、w=6 で 2/20。NNのスコア差 0.1〜0.2 × w が手作り項との綱引きに
  勝つ必要がある）
- state特徴量は候補間で共通なので粒子単位に遅延キャッシュ、粒子数は
  `nn_samples`（思考予算比例、基準48）で制限
- 再学習の手順は opp_move NN と同じ（記録用アリーナ → `export_value_data` +
  `export_pairwise_data` → tsuitate-nn/train.py を pairwise w=20 m=0.1 で
  **4シード** → gold-check/kakudo オフライン検証で両正解シードを選ぶ →
  `export_value_weights.py` → クロスチェック期待値再生成 → w スイープ →
  ガントレット）。**定石更新時はデータ再生成**（opp_move と同じ教訓）

限界の認識: valueネットは「明確な悪手の回避」（gold-check系）には効くが、
「無目的な安全手同士の序列」（54手目9二香のような横並び）はまだ判別しない。
以下はフェーズ1（データ基盤とオフライン学習、2026-07-20〜21）の記録。
