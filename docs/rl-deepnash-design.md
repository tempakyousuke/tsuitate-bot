# DeepNash（R-NaD）路線: RL 環境の設計（2026-09-27）

> 種類: 設計。状態: **提案（未実装）**。NN 段階④（フルRL）の着手。

## 背景と方針

- ついたて将棋 viewer に、作者・出所不明の DeepNash 系とみられる bot が現れ、強かった。
  解説記事はなく、作者にも聞けないので手探りで進める。
- 対局した印象（ユーザー観察）:
  - 1手の消費時間は一定で短い → **探索も粒子も使わない、観測履歴から直接手を出す方策ネット**と推定
  - 指し手はある程度散るが、やり口は似ている → 学習済みの混合戦略として自然
  - 反則をしないというより**攻めが上手く、こちらの反則を使わされる**
  - 終局は詰みと反則負けが同程度
- 3つ目は、手書きの評価では届かなかった領域そのもの（`check_strength_w` の結論:
  「選好を入れ替えるだけでは相手の反則総量は動かない。強い王手が成立する形を
  **作る**中期的な項が要る」）。RL なら、報酬が勝敗だけでも反則負けを誘う攻めが自然に出てくる。

**方針**: 学習は R-NaD（DeepNash の中核アルゴリズム）。環境・評価は既存の Rust 資産を流用し、
**物差しは今までどおり arena の凍結版ガントレット**にする。現行 bot は、新方式が v14 に
有意に勝ち越すまで本番に残す。

## 全体構成

```
tsuitate-bot（このリポジトリ）
├─ src/referee.rs      … 手単位で進める審判（selfplay.rs のループから切り出す）
├─ src/rl/encode.rs    … 観測 → テンソル、行動 ⇄ USI、行動マスク（依存は std のみ）
├─ src/rl/policy.rs    … ONNX 方策を読む Strategy（arena・本番用、名前は `rnad`）
└─ rl-env/             … PyO3 の薄いラッパー crate（maturin でビルド。本体の依存は増やさない）

tsuitate-nn（学習側）
└─ rnad/               … R-NaD 本体（PyTorch）、ネット、ONNX 書き出し
```

**不変条件: エンコーダは1か所だけ**。入力は `Strategy::choose` と同じ
`(PlayerView, ObservationLog, foul_tried)` にする。学習中の環境（Python 経由）も
arena・本番の `rnad` Strategy も同じ Rust 関数を呼ぶので、「学習時と推論時で特徴量が
食い違う」事故が構造的に起きない。観測情報の公平性も、今の arena と同じ構造で守られる
（エンコーダは observation.rs にある情報しか受け取らない）。

## 1. 審判（referee.rs）

`selfplay::play_game_with_oracle` は戦略を呼ぶループと裁定が一体になっている。
RL では「行動を1つ受け取って1歩進める」形が要るので、裁定部分を切り出す:

```rust
pub struct Referee { pos, logs: [ObservationLog; 2], fouls: [u32; 2], foul_tried: [HashSet<String>; 2], plies }
impl Referee {
    pub fn to_move(&self) -> Color;
    pub fn view(&self, color: Color) -> PlayerView;
    pub fn step(&mut self, usi: &str) -> StepResult; // Accepted / Foul / Ended(GameResult, reason)
}
```

- 裁定は今と完全に同じ: 反則は手番維持・`OpponentFoul` を相手へ・10回で負け、
  受理なら `MyMove` / `OpponentMoved`（取られたマス）/ 王手宣言を両者へ、詰み・
  ステイルメイト、`MAX_PLIES`=200 で引き分け
- **`play_game_with_oracle` は `Referee` を呼ぶ形に書き換え、裁定の実装を1つにする**。
  等価性は「seed を固定した heuristic 同士の対局で、書き換え前後の観測ログと真実が
  一致する」テストで担保する（CLAUDE.md の「観測の作り方は selfplay.rs と一致させる」を
  二重実装で破らないため）
- `Referee::from_start(StartState)` で途中局面からも始められるようにする（4b の指し継ぎ用。
  checkpoint arena の `play_continuation` も同じ入口へ寄せる）
- 時計は RL 環境では持たない（方策ネットは一定時間で指すので不要）。arena 側は従来どおり

## 2. 観測エンコード（rl/encode.rs）

**手番側を常に先手向きに正規化する**（後手なら盤を180度回す）。ネットは「自分が
下から攻める」局面しか見ない。

### 盤面プレーン（9×9）

| 群 | 枚数 | 中身 |
| --- | --- | --- |
| 自駒 | 14 | 駒種ごと（玉・飛・角・金・銀・桂・香・歩＋成駒6種） |
| 自分の着手履歴 | 2×K | 直近 K 手（K=8）の移動元・移動先。打ちは移動先のみ。線が開いた/塞がった情報の元 |
| 自分が取った駒 | 1＋7 | 取ったマスの鮮度（exp 減衰）＋取った駒種ごとのマス |
| 自駒が取られたマス | 2 | 鮮度（exp 減衰）と回数。**相手の駒が確実にいた場所**の唯一の直接観測 |
| 今の手番の反則試行 | 3＋7 | 移動元・移動先・成りの移動先、打ちは駒種ごとの打ち先。「この手は通らない」＝相手駒の存在や王手の証拠 |
| 過去の反則 | 3＋7 | 今の手番と同じ形を鮮度つきで。**打ちの駒種と成りを落とさない**（同じマスでも歩打ちの反則には打ち歩詰めという別の原因があり、隠れた盤面への証拠が違う。codex レビュー指摘） |
| 王手宣言の履歴 | 2 | 自分が王手されたときの自玉の位置、自分が王手をかけた手の移動先（どちらも鮮度つき） |
| 初期配置から未着手の自駒 | 1 | 定跡・囲いの判断用 |

実装（`src/rl/encode.rs`）では下のスカラーを全面に放送したプレーンも含めて **86 枚**。
鮮度の減衰率・K は最初は固定値にし、後から調べる。
反則の移動元と移動先の**対応**（どの移動元の手がどの移動先で反則したか）はプレーンでは
表せず、同じ手番に複数の反則があると混ざる。困ったらイベント列の入力で扱う（履歴の持ち方の節）。

### スカラー（全マスへ放送してプレーンにする）

- 自分の持ち駒 7種（枚数を正規化）
- 相手の**駒種別保有数（盤上＋持ち駒）**: 駒種の総数 − 自駒 − 自分の持ち駒。平手なら
  **視界だけから確定する**ので履歴が欠けても正しい（持ち駒と盤上の内訳は、相手の打ちが
  観測できないので分からない）
- **履歴の食い違い**: 観測ログから再構成した自駒・持ち駒が視界と一致しなければ 1。
  本番でプロセス再起動により履歴を失った場合などに、履歴由来の特徴が信用できないことを知らせる
- 自分の反則数・相手の反則数（0〜9 を正規化＋「あと1回で負け」の指示子）
- 今の手番で既にした反則の回数
- 王手されているか・直前に王手をかけたか
- 手数 / 200

### 履歴の持ち方について

本家 DeepNash は再帰を使わず、観測に履歴の要約を入れている。まずそれに倣って
**固定長の要約（上の減衰プレーン）**で始める。学習が頭打ちになり、原因が「記憶不足」と
見えたら、イベント列を読む Transformer に置き換える（その時点で判断）。

`belief_features.rs`（観測だけから作る 35 特徴量。1決定点 81 回の計算で安い）を
追加プレーンとして入れる選択肢もある。学習が速くなる見込みがあるが、まずは素の観測で
始めて、比較実験として足す。

## 3. 行動エンコード

AlphaZero（将棋）と同じ **139 枚 × 81 マス = 11,259 行動**:

- 移動元のマス × 移動の種類 139:
  - 8方向 × 距離 1〜8 = 64、桂の2方向 = 2、それぞれ不成/成 → 132
  - 打ち 7種（このとき「マス」は打ち先）→ 7
- 手番側を先手向きに正規化してから符号化する（後手でも「前」は常に同じ方向）

### 行動マスク

- `board.rs` の**自駒だけを見た候補手**（`move_targets` / `drop_targets` /
  `promotion_choice`。成り・不成・強制成りを展開）から、**今の手番で既に反則した手を除く**
- 見えている範囲で確定する反則（二歩・行き所のない駒・自駒のマスへの移動・自駒を
  飛び越える移動）はマスクで落ちる。見えない相手駒による反則はマスクに入らない
  （それを学ぶのがネットの仕事）
- **健全性の検査を常設**: ランダム対局の全局面で「真の合法手 ⊆ マスク」をテストする。
  マスクから真の合法手が漏れると、その手を永久に指せない方策になるため

## 4. 報酬とエピソード

- **終局時だけ ±1、引き分け（200手）は 0**。反則・駒得・王手に途中報酬は付けない
  （反則を誘う攻めは勝敗だけから出てくるはずで、途中報酬はそこへ偏らせる）
- 反則した場合、次の手番も同じプレイヤーになる。R-NaD は一般の展開形ゲームを扱うので、
  同じプレイヤーが続けて行動しても問題ない
- 1局の長さは最大 200 手＋反則 18 回

### 報酬を勝敗だけにする理由（2026-09-27 ユーザーとの議論）

「惜しい負け」「辛勝」を報酬で区別したくなるが、区別の物差しは駒得や手数になり、
**駒得を報酬に混ぜると頓死を軽く罰する方向へ働く**（駒得して追い詰めた末の頓死は、
駒得分だけ「惜しい負け」になってしまう）。勝敗だけなら、駒得していようが頓死は −1 で、
方策は「駒得しても玉が危ないなら意味がない」を学ぶしかない。
「惜しさ」は価値ヘッドの出力（勝率の見積もり）として自然に表れるので、報酬に入れる必要はない。

ただし勝敗だけの報酬は信号が薄く、学習が遅い。そこで**目的は変えずに学習を速くする**
補助タスクを付ける（損失に足すだけで報酬には入れない。推論時には使わない）:

- **真の盤面の予測**: 相手駒の位置・駒種、相手玉の位置。学習時は審判が真実を知っているので教師にできる。
  入力は観測だけなので、推論時に情報が漏れることはない（信念ネット＝段階②の知見を、
  別のネットでなく共有の表現として取り込む形）
- **近い将来の詰みの予測**: 「N 手以内に自玉が詰まされるか / 相手玉を詰ませるか」（N=1,3,5）。
  頓死の手前で「危ない」という表現を早く作らせるため
- 駒の損得の予測（補助。報酬には入れない）

報酬の整形がどうしても要る場合は、最適方策を変えないことが保証されるポテンシャル型の
整形だけにする（今の時点では使わない）。

## 4b. 途中局面からの指し継ぎ（逆向きカリキュラム）

勝敗だけの報酬は終局で1回しか出ないので、序盤の手ほど信号が遠く、学習が遅い。
そこで**対局の終盤から指し継ぐ**エピソードを混ぜ、信号の近いところから学ばせる。
開始点を少しずつ手前へずらしていく（逆向きカリキュラム。一本の実演の終わり近くから
始めて開始点を戻していく手法が、報酬の疎な課題で有効だったのと同じ考え方）。

当初は「頓死した局面を拾う」形で考えたが、頓死の機械的な抽出は難しい
（`mate_economy` の定義は一手詰め基準で、長手数の頓死を拾えない）。**無作為に選んだ
対局の終盤から始めれば定義は要らず**、頓死も詰ませ損ないも反則負けの手前も
自然に含まれる（2026-09-27 ユーザー提案）。頓死の抽出は、後で重み付けとして足す選択肢に格下げする。

### 情報不完全ゲームでの「局面」

ついたて将棋では局面＝盤面ではなく、**真実の盤面＋両者の観測履歴**の組になる。
これは既に `selfplay::StartState`（真実の盤面・両者の観測ログ・累積反則数・手数）として
あり、checkpoint arena（issue #19）が同じ仕組みで途中から指し継いでいる。
記録からの復元は `truth_replay`（両者の観測列の再構成）が担う。
`Referee` を `StartState` から作れるようにすれば、そのまま使える。

### 開始点の選び方

- 開始点は「終局の k 手前」で決める。k は `[0, K]` から一様に選び、**K を学習の進み具合に
  合わせて広げる**（例: 開始時 K=20 → 終局付近の勝率予測が安定したら 40, 80, …、最後は
  対局の頭まで = 通常の対局と同じ）
- 同じ開始点から何度でも指し継げる（方策はサンプリングなので毎回違う展開になる）。
  1つの記録から多数のエピソードが取れる
- 反則数が9に達している開始点は、そこから数手で反則負けになりやすい。除かずに残すが
  （「あと1回で負け」の状態で指す練習になる）、比率が偏っていないかは監視する

### 開始点の出どころ

1. **既存の記録（初日から使える）**: arena-records（v14 の自己対局）
2. **自分の対局（学習が進んでから）**: 学習中の自己対局をそのまま記録して開始点にする

1. には偏りがある: そこに至る履歴は v14 の指し方で、**履歴から推測すべき隠れた情報の
分布も v14 の相手が作ったもの**になる。ネットは「この観測なら相手駒はこの辺」を
v14 の癖で覚えてしまう。これは開始点が情報不完全ゲームであることに固有の問題で、
完全情報ゲームなら起きない。なので 1. は立ち上げ用と割り切り、**自分の対局が溜まったら
2. へ切り替える**。2. なら履歴も隠れた情報も今の方策が作ったものなので偏りはない。

### 注意点

- **通常の対局と必ず混ぜる**（例: 通常 50% / 指し継ぎ 50% から始め、K が広がるにつれて
  指し継ぎの意味は薄れていく）。指し継ぎだけにすると序盤・中盤が育たない
- 頓死した側だけでなく、**詰ませた側の視点**も同じ指し継ぎから学べる
  （両者を同じネットで学習するので、攻め側の「頓死を狙う」力も同時に育つ）
- 価値ヘッドが育ったら、開始点を「予測が外れた対局」（勝勢の見込みから負けた＝頓死・逆転）
  に寄せる重み付けを足せる。手で頓死を定義しなくても、ネット自身の見込み違いで拾える

## 5. Python 環境（rl-env crate）

- `VecEnv(n)`: n 局を並列に持つ。`reset()`、`observe() -> (obs[n,C,9,9], mask[n,11259], player[n])`、
  `step(actions[n]) -> (reward[n,2], done[n])`
- ネットの推論はバッチで1回、環境の更新は Rust 側で rayon 並列
- 対戦相手を Rust の既存戦略（heuristic・凍結版）にする評価モードも持たせる
  （学習ループの中で「heuristic に何割勝つか」を安く測るため）

## 6. 学習（tsuitate-nn/rnad）

- R-NaD を PyTorch で実装する（OpenSpiel の JAX 実装 `rnad.py` を参照。手元の Mac では
  PyTorch の MPS のほうが扱いやすい）。要素: 正則化方策との対数比による報酬変換、
  v-trace、NeuRD 更新、正則化方策の定期更新
- ネット: 9×9 の ResNet（まず 6 ブロック × 64ch 程度、パラメータ 50万前後）、
  方策ヘッド 139 枚、価値ヘッド
- ONNX で書き出し、Rust 側は `tract-onnx`（純 Rust で CI ビルドが楽）で読む

### M0 の実装状況（2026-09-27、ブランチ `rl-deepnash-m0`）

- `src/referee.rs`: 手単位の審判。`selfplay::play_game_with_oracle` はこれを呼ぶ形に
  書き換え、裁定の実装は1つになった。**切り出し前後の等価性**は、seed つき乱数方策の
  48局（オラクルなし・両者 nofoul・片側 nofoul・両者 check_nofoul の4条件。終局は
  反則負け・詰み・200手引き分けを含む）で、観測ログ・視界・真実・終局を丸ごと
  sha256 したダイジェストが切り出し前のコードと一致することで確認した
  （`selfplay::tests::審判の切り出し前後で裁定と観測が一致する`）
- `src/rl/action.rs`: 139×81 の符号化とマスク。全行動の往復一致・先後の対称性・
  **ランダム40局の全局面で真の合法手 ⊆ マスク**（1万手以上を検査）をテストで常設
- `src/rl/encode.rs`: 86 枚。初期局面で先後のテンソルが一致すること・反則/捕獲/保有数が
  載ること・王手の履歴が両者に載ること・手番が変わると反則が過去へ移り打ちの駒種と成りが
  残ること・履歴の食い違いの印・値域をテスト。速度は release で **平均 34µs/決定点**
  （エンコード＋マスク。履歴を毎回先頭から辿る実装のままで、1コア約3万決定点/秒）

### codex レビュー（2026-09-27）で直したもの

- **終局手のフィッシャー加算漏れ**（退行）: 旧実装は受理手の適用直後・終局判定の前に加算して
  いたが、切り出し直後は `Accepted` にしか加算していなかった。`StepResult::Ended` に
  `move_accepted` を持たせて詰み・ステイルメイト・手数上限の手にも加算する。等価性ダイジェストは
  時計なしで回すので `selfplay::tests::終局手にもフィッシャー加算が付く` で別に固定
- **開始時点で終局済みの局面**: `Referee::from_start` が終局を判定して `ended()` に持ち、
  以後の `step` は何も記録しない（逆向きカリキュラムの k=0 は終局そのものを開始点に選びうる）
- **過去の反則で打ちの駒種と成りが消える**: 今の手番と同じ 3＋7 枚の形で持つ
- **履歴が欠けると誤った特徴を確定値として出す**: 相手の保有数を視界だけから出す形に変え、
  履歴の食い違いの印を足した
- 等価性ダイジェストは「終局手で追加された最後の観測」を採取しない（次の `choose` で採るため）。
  終局手も通常の受理手と同じ `accept` を通るので実害は低いと判断し、ダイジェストは据え置いた

### M2a の実装（2026-09-27、ブランチ `rl-deepnash-m2a`）

- **教師**: 日次の Mine tsume（現行 estimator 対 v14 の自己対局 160局/日、記録は90日保持）の
  `arena-records-mine-*`。`tsuitate-nn/rnad/fetch_records.py` が `data/rl_records/<run_id>/` へ取る
  （30日で 4,800局・試行 53万件）
- **`src/rl/records.rs`**: 真実（全手順＋反則試行）を**試行ごとに** `Referee` へ流し直し、各試行の
  直前の審判を渡す（反則した試行も教師にする）。観測は arena と同じコードで作られる。
  ランダム局で「再生 = 元の対局」、実記録 20局（2,212試行）で「再生した観測 = 記録された観測」
  を確認済み。`RecordDataset` は読み込み時にこの一致を全局で検査し、食い違う局は捨てる
- **`rl-env` の `RecordDataset`**: 局単位で並列にエンコードして numpy で返す（観測・マスク・
  教師の行動・手番・価値の教師＝手番側から見た終局の結果・反則だったか）
- **`tsuitate-nn/rnad/`**: `model.py`（ResNet。方策 [139,9,9]・価値 tanh）、`train_bc.py`
  （局単位で学習/検証を分ける。マスク付き交差エントロピー＋価値の MSE）、
  `export_weights.py`（BatchNorm を畳み込みへ畳み込んで `TSRLPV01` 形式で書く）
- **`src/rl/policy_net.rs`**: 手書きの forward pass（依存を増やさない）。小さいネット
  （BatchNorm の統計も乱数）で PyTorch の出力と一致することをフィクスチャ
  （`tests/fixtures/rl/tiny_policy.*`）で常時検査。64ch×6ブロックで 1手 約13ms
- **`src/rl/policy.rs`**: 方策ネットで指す戦略。`strategy::make("rl_policy:<重みのパス>")`
  （softmax からサンプリング）/ `rl_policy_greedy:<パス>`（最大の手）。重みはパスごとに1度だけ読む

**codex レビュー（2026-09-28）で直したもの**:
- [P0] 記録の勝敗を再生の裁定と照合していなかった（勝者を取り違えた記録・読めない結果文字列・
  途中で切れた記録が価値の教師を汚す）→ `records::verify_outcome`。審判が判定する終局
  （詰み・ステイルメイト・反則負け・手数上限）は勝敗と理由の完全一致、審判の外の終局
  （時間切れ・投了）は再生が未終局であることを求める。実データ 4,800局は全局通過
- [P0] 学習率スケジュール（OneCycleLR）の総更新数が実際の更新回数とずれていた（局の長さが
  不揃いで端数バッチが出る）→ 処理した標本数を進み具合にした warmup＋cosine
- [P1] 対局記録から使った重みを特定できなかった → 重みの内容の sha256 で識別し、`name()` を
  `rl_policy@<先頭12桁>` にした（同じパスを上書きしても別の戦略として記録される）。
  chose の debug にも sha256 を入れる
- [P1] 取得が途中で切れた run を取得済みと判定していた → 全 artifact を取り終えたら `.complete`
- [P2] 同じ棋譜（着手列＋反則試行列が完全一致する局。4,800局中13局ぶん）が学習と検証の両方に
  入りうる → 棋譜の署名でまとめて分ける
- [P2] エンコードのメモリ → 結合先を先に確保し、学習側はチャンクごとに手放す
- 特徴量・行動の並び・BatchNorm の畳み込み・Rust の畳み込みのインデックスの一致と、
  入力へ真実が漏れていないことは codex も確認済み

### 重みの置き場所（2026-09-28 ユーザー判断）

重みは差分圧縮が効かず（学習し直すと全部の値が変わる）、コミットのたびに履歴が
約2MB（64ch×6ブロック）ずつ永久に増える。ネットを大きくすれば1個10MB を超える。
そこで次のように使い分ける:

- **実験中の重み → GitHub Release**（prerelease、タグは `rlw-<内容>-<日付>`）。arena では
  戦略名に `rl_policy:release:<タグ>/<ファイル名>` と書くと、arena ジョブが
  `scripts/ci/resolve_rl_weights.sh` で取ってきて手元のパスへ置き換える（候補・基準のどちらにも書ける）。
  例: `gh workflow run arena.yml --ref <ブランチ> -f candidate="rl_policy:release:rlw-bc-m2a-20260928/policy.bin" -f match_seed=...`
- **採用した版だけリポジトリへコミット**（`models/`、凍結版と同じ扱いでガントレットの基準にする）
- Git LFS は無料枠の転送量（月1GB）を CI のダウンロードが食うので使わない
- 使った重みは記録上の戦略名（`rl_policy@<sha256 先頭12桁>`）と Release のノートの sha256 で照合できる

M2a を先に置く理由: RL は「学習が進まない」ときに原因の切り分けが難しい。教師ありは
うまくいくはずの課題なので、ここでエンコーダや配管のバグを先に潰しておく。
M2a の模倣方策で R-NaD を初期化するかどうかは、M2b でゼロからの学習の伸び方を見て決める
（初期化すれば計算量は大きく減るが、v14 の癖を引き継ぐ）。

### M2b の実装と最初の計測（2026-09-28、ブランチ `rl-deepnash-m2b`）

- **`tsuitate-nn/rnad/rnad.py`**: R-NaD の PyTorch 実装。OpenSpiel の rnad.py（2025-05 に
  OpenSpiel から削除されたので、削除直前の d1dcdf5）の移植で、**損失と勾配が参照実装と一致する**
  ことを、参照実装（使い捨て venv の JAX）で乱数入力から計算したフィクスチャ2組で検査する
  （`rnad/tests/`。反則で同じプレイヤーが続く並び・長さの違う局・引き分けを含む）。
  参照との違いは持ち方だけで、行動数 11,259 の Q ベクトルを作らずアドバンテージを
  `−η(lpr_a − Σπ·lpr) + s(1[a=選んだ手] − π_選んだ手)` に分解して持つ
- **`rl-env`**: `VecEnv(auto_reset=False)`・`reset()`・`alive()`（1局を丸ごと集めるため。
  止まった局の行動は -1、マスクは空）
- **`train_rnad.py`**: 64局を最後まで自己対局 → 1更新（約7〜8秒）。進み具合は**錨（模倣ネット）との
  直接対戦**で測る（凍結版は1手1秒以上かかり学習ループに入れられない）

**1回目（参照の既定 β=2、300更新）は失敗**: 錨への勝率は横ばいに見えたが、評価に使っていた
ターゲットネットは現在のネットにゆっくり追従するだけで（300更新で約26%）、**現在のネットは錨に
23% まで弱くなっていた**。原因は **NeuRD のしきい値 β**（合法手の平均を引いたロジットが ±β を
超える方向へは押さない）。参照の既定 2.0 は小さいゲーム用で、模倣ネットの最善手は平均より
+6.6（中央値。99% 点 +14.9）にある。β=2 ではこれが押し下げられ、300更新で最善手 +3.7・
±2 の内側の合法手 67% → 90% と**方策が平らに潰された**。
→ **β=16**（模倣ネットの広がりより上）にし、評価は**現在のネットとターゲットの両方**を記録する。

**2回目（β=16、300更新・自己対局 19,200局、約45分）**: 劣化は止まった。錨への勝率（256局×12回の合算）は

### 案: 真実を見る価値ネットをベースラインにする（序盤の信用割り当て）

**問題**: 今の設定（集めた直後に1回更新 = π/μ ≈ 1）では v-trace の目標は実質モンテカルロで、
各手のアドバンテージは `最終結果 − V_観測(手を選ぶ前)` になる。1局の全部の手が同じ ±1 を
浴び、手ごとの差はベースラインだけから生まれる。序盤ほど終局が遠く、隠れた配置の運による
分散も大きいので、序盤の手の信号が薄い。逆向きカリキュラム（4b）は終盤・中盤から効くが、
序盤には最後に届く。

**当初の案（採らない）**: 中盤（駒がぶつかり始めて10手後など）で、真の盤面と残り反則数から
優劣を判定する手書きの審判で打ち切り、その判定を報酬にする。採らない理由:
- 序盤の方策が審判の物差し（駒得・反則数）の最大化へ育つ。4節で駒得を報酬に混ぜないと
  決めた理由の再来で、手書きの「有利」が勝率と噛み合わない実例もある（駒得 +340点/50局で
  勝率不変、評価項10件が勝率に変換されず）。R-NaD の収束先も打ち切った代わりのゲームの均衡になる
- 真の盤面には「誰が何を知っているか」が無い。ついたて将棋の序盤の価値の多くは情報
  （駒の隠し方・探り・玉位置を掴ませないこと）にあり、それを数えない審判は情報のための手を
  過小評価させる

**採る形**: 真実を見る価値ネット V_真実 を学習し、報酬ではなくアドバンテージのベースラインに使う。

```
s(t) = 最終結果 − V_真実(t の局面)     （今は V_観測(t)）
```

- 入力: 真の盤面＋**両者の観測履歴**＋残り反則数（= `StartState` と同じ、局面の完全な状態。
  両者の観測履歴を入れるので情報面の優劣も入力に含まれる）。教師は実際の勝敗
- 手は観測だけから選ばれるので、隠れた状態に依存するベースラインでも期待値ではゼロの項 =
  **不偏**。報酬は勝敗のまま
- 隠れた配置の運による分散を差し引けるので、序盤の雑音が減る
- 学習時だけ使い、推論（方策ヘッド）には入らない（非対称 actor-critic）。公平性の構造は不変
- 足りなければ、V_真実 で中盤に打ち切ってブートストラップする（v-trace の c < 1 や打ち切り点）。
  序盤の信号は最も強くなるが、V_真実 が未熟なうちは偏りが入るので、**ベースラインだけ → 打ち切り**の順で試す

**先に測ること**: arena-records（4,800局）で V_真実 だけを教師ありで学習し、手数ごとに
最終結果の予測精度（対数損失・AUC）を測る。`records.rs` の再生と `RecordDataset` を流用できる。
- 30手目でも十分当たる → 序盤で勝敗がかなり決まっている。ベースラインが序盤に強く効く見込み
- 30手目でほぼ当たらない → 序盤はまだ勝敗に効いていない。序盤より終盤・中盤を優先する判断材料
- 対照として同じ手数の V_観測（観測だけの価値）も測り、差 = ベースラインで削れる分散の目安にする

### 案: 報酬を変えたスタイル特化モデル（入玉特化から）

**狙い**: 報酬に戦法のボーナスを足して、特徴を持つモデルを作る。用途は2つで、両方を1本の系統で賄う。
- **本命を強くする練習相手（リーグ）**: 本命を「自分自身＋スタイル特化モデルの混合」と対戦させ、
  特定の戦法への穴を塞ぐ。入玉は相手に玉の位置を掴ませにくく、ついたて将棋では実戦的な戦法
  （quest_20260731 のレビューにも「今入玉を目指すと相手はこちらの王様の位置を見つけられない」）。
  自己対局だけでは試されにくい戦法ほど、練習相手としての価値が高い
- **人間向けの個性ある bot**: サイトで選べる相手など。こちらはある程度の強さも要る

**前提**: 入玉は今の自己対局ではあまり起きていない（ユーザーの感覚的な予想。未計測）。
`referee.rs` に入玉宣言の裁定は無く、終局は詰み・ステイルメイト・反則負け・200手の引き分け（`max_plies`）だけ。

**報酬の形**:

```
報酬 = 勝敗(±1) + λ(t) · 入玉ボーナス
```

- 入玉だけを報酬にしない。勝敗を無視して玉を突進させ、詰まされるモデルになる。
  **勝敗の報酬は最初から残す**（詰みを無視する癖と、入玉を過大に見る価値ネットを育てないため）
- 入玉の定義（敵陣3段目以内に到達した時点で1回だけか、終局時にいれば付けるか）で挙動が変わる。最初に決める
- R-NaD はゼロ和2人ゲームが前提で、片側だけにボーナスを足すと収束保証が外れる。選択肢:
  - ゼロ和のまま足す（入玉した側 +λ・された側 −λ）。相手も入玉の止め方を覚えるので、
    できるのは「入玉を巡る攻防が強いモデル」
  - 本命を固定し、その相手への最善応答として学習する（1人用 RL になり理屈がきれい。
    `rl/env.rs` の評価モードを NN の相手にも広げる）
  - 両側ともボーナス付きの自己対局（動くと思うが保証なし）
- 本命（M2b 以降の重み）から微調整すると安い。π_reg を本命に固定すれば、η が
  「本命からどこまで個性を出してよいか」のつまみになる

**λ のアニーリング（発見 → 使いどころの判断）**: 入玉は隠れた敵陣を抜けて玉を6段ほど運ぶ長い手順で、
サンプリングした方策が偶然やり切ることはまずない。そのため勝敗の報酬が「入玉すると勝てるか」を
評価する機会自体がない。λ を大きく始めて入玉を安定して実行できるようにし（技術の獲得）、
λ を下げて使いどころを勝敗に判断させる。
- λ を変えるのは正則化方策の差し替え（`EntropySchedule` の区切り）に合わせる。各区間は
  「固定したゲームで収束させる」前提なので、区間の途中で報酬を動かさない
- λ を下げると、勝敗で得でなければ入玉を捨てる（自己対局では相手も止め方を覚えるのでなおさら）。
  本命にとっては正しい判断で、発見の段階は無駄にならない
- **同じ学習を途中で分岐させる**: λ が高い段階の重みを練習相手に、λ に下限（例 0.3）を残して
  止めたものを個性 bot に、λ を下げ切った先を本命にする
- 入玉は引き分けに流れやすい（入玉宣言が無く、勝ち切れなければ200手で報酬0）。λ を下げた段階で
  「入玉して寄せる」まで学ばないと入玉の価値は勝敗から見てゼロに近く、捨てられやすい。
  入玉した局の終局理由の内訳を監視する
- 報酬を変えずに発見を助ける手段として、逆向きカリキュラム（4b）の開始点に「玉が中段まで出ている
  局面」を混ぜる方法もある。ただ記録に入玉が少なければ開始点が集まらないので、
  **アニーリングで作った入玉局を開始点に再利用する**組み合わせが現実的

**確かめ方**:
1. 入玉の頻度を数える: 現在の R-NaD の自己対局と v14 の記録で、入玉率と入玉した局の勝率を比べる。
   稀なら「発見が律速」の前提が立つ
2. 同じ計算量で3つの arm を比べる。A: 勝敗のみ / B: 固定の小さい λ / C: λ のアニーリング（大 → 小）。
   見るのは入玉率・入玉局の勝率と終局理由・錨（または v14）への勝率。
   C が A より錨に強ければ「発見を先にすると学習が早い」、C が入玉を保ったまま A と同等の強さなら
   個性 bot の候補
