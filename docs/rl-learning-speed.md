# 学習の速さの比較と、速く強くなる学習方法の実験（2026-10-20）

> 種類: 設計/記録。状態: **比較方法の提案と、CPU での診断・代理実験の結果**。本線（ゲーム用 PC の R-NaD）は止めずに、
> 別の計算資源で「同じ計算量でより強くなる学習方法」を探すための物差しと、その最初の試行。
> 学習側のコードは tsuitate-nn のブランチ `claude/admiring-carson-1hwun6`（**どれも既定は従来と同じ**。本線の再開に影響しない）。
> 計測はクラウドの CPU 4コア（GPU なし）。本線と同じ規模の学習は回せないので、学習なしの診断と小さい代理で測った。

## 要点

1. **本線は「勾配の雑音」で律速されている**（学習なしの診断、rl_deduce_v4）。1局ごとの勾配の分散に対して期待勾配が小さく、
   雑音のスケール B_noise（勾配の向きが雑音に埋もれない局数）は **数千〜2万局**（384局では期待勾配が誤差の内で、点推定は
   約9,000局、別の推定では約17,600局。下限の目安）で、1更新の 768局よりずっと大きい。
   段階ごとの伸びが縮み、段階の中で KL が酔歩のように線形に伸び続ける、という本線の観察と合う
2. **その雑音のほとんどは「まれにしか選ばれない手」から来る**。v-trace の s = (結果 − v)/μ の2乗和の **99.6〜99.9% を、
   確率 μ < 0.001 の手が選ばれた 0.1〜0.3% の決定点**が占める（その手の平均のアドバンテージはほぼ 0）。NeuRD のクリップ 10,000 は
   事実上効いておらず、本家は β=2 で方策を混合のまま保って 1/μ を間接的に抑えていたが、β=16 の本線には抑えが無い。
   このスパイクが Adam の2次モーメントを幹全体で決めてしまい、価値の損失・正則化の引きのほうは幹にほとんど届かない
   （幹の Adam の v に占める割合: s の項 100%、価値 5×10⁻⁶、正則化 7×10⁻⁵）
3. **数式を変えない高速化で 1更新 14.9秒 → 約8秒の見込み**（合法手に詰めた更新・重み 0 の正則化ネットの省略・
   自己対局と更新の重ね合わせ。どれも実装済みで、省略は常に有効〔結果はビット単位で同じ〕、残り2つは既定オフ。GPU での確認が残る）。
   **RTX 3070 の実測（2026-10-21、7.1 節の末尾）**: `--packed --compact-legal` は学習が従来と同じで 1更新 約15.2秒 → 約13.5秒。
   `--pipeline` を足すと約8.7秒（約1.7倍）になるが、1更新遅れの方策で集めるぶん v-trace の目標が変わり（`loss_v` 1.78 → 約1.0）、
   **数式を変えない高速化ではなかった**。採るなら学習曲線の A/B が要る
4. **比較の物差し**: 学習中の錨や直前の版との直接対戦は使わない（直前の版との直接対戦は、直近7段階で進歩を約4.5倍に見せていた）。
   固定パネル（凍結版、レートは ratings.json に固定）に対する Elo を、更新回数・決定点数・基準機の秒数の関数として並べる。
   本番規模の1段階 A/B は「2倍速い」方法でも検出力が約3割しかないので、**安い代理でふるい、GPU では少数を確かめる**
5. **CPU の代理実験（6節）**: rl_deduce_v4 を小さいネットへ蒸留した出発点（P2）から比べると、本線と同じ学習率（1e-4）では
   どの腕も 400更新（25,600局）で出発点を有意には超えず、速さの差は測れなかった。学習率を上げると、上限なしの対照は雑音で
   壊れる（3e-4 で −54、1e-3 で −125 Elo）が、**1/μ の上限 100 は壊れ方がずっと小さい**（3e-4 では出発点のまま・200更新で
   対照より +44 Elo〔2 seed。ただし差が出たのは対照が落ちた 200更新で、50〜200 の合算は +2.5 ± 1.1pt〕、1e-3 では上限 100 も
   −40〜−50 Elo 下がるが対照より +10.4 ± 1.5pt）。PG（3e-4 だけ）も壊れなかった。クーンポーカーの厳密な NashConv では、上限 100 は参照と区別できず（偏りは見えない）、
   上限を強くする（20・5）ほど収束が遅れた。→ **学習方法の GPU の A/B の最初の候補は「1/μ の上限 100」と「上限 100 + 学習率 2e-4」**
   （その前に、数式を変えない高速化と学習に影響しない書き出しを入れる。8節）

## 1. 何を「速さ」とするか

**強さ（固定パネルの Elo）を計算量の関数として**並べ、同じ Elo に届くまでの計算量の比（速度比 M）で比べる。
横軸は3つ取り、どこで速くなったかを分ける:

| 横軸 | 何が分かるか |
| --- | --- |
| 更新回数 | 1更新あたりの賢さ（アルゴリズム） |
| 決定点数（標本数） | 1標本あたりの効き（分散を減らす手・標本の使い回し）。局数より決定点数（局の長さは学習で 117手 → 60手台まで縮む） |
| **基準機の秒数（主）** | ゲーム用 PC（RTX 3070）での壁時計。律速の資源はこの PC の時間なので、最終的にはこれで比べる |

- 基準機の秒数は **CPU で測った壁時計を使わない**（このコンテナでは同じ設定でも負荷で 1更新 13〜280秒に振れた）。
  ゲーム用 PC の実測からのコストモデル（1更新 ≈ 0.9秒 + 5ms × 局数 + 0.134ms × 決定点数 × 順伝播の回数/9）で換算し、
  重ね合わせ（`--pipeline`）のようにモデルが当てはまらない変更は基準機で直接測る（`rnad/bench_update.py`）
- 数式を変えない高速化（下の 5節の A 群）は学習曲線を取り直す必要がない: 勾配の一致をテストで確かめ、基準機で1更新の秒を測るだけ
- 要約: (a) 速度比 M（対照の伸びの 25〜90% の範囲の Elo で、同じ Elo に届く計算量の比の幾何平均）、(b) 予算の終わりの Elo
  （同じ計算量で）、(c) log(計算量) で平均した Elo。標準誤差は**学習の seed の間のばらつき**から出す（同じ run の書き出しどうしは
  相関するので独立に数えない）

## 2. 物差し: 固定パネルの Elo

- **使わないもの**:
  - 学習中の錨への勝率（run ごとに錨が違い比べられない。錨が弱くなると 88〜95% で頭打ちする）
  - **直前の版との直接対戦**。直近7段階（46,000〜58,000更新）で、直接対戦から換算した伸びの合計は +475 Elo だが、
    全パネルの BT では +105、別系統どうしの対局だけで当て直すと +44（自分の系列への特化が乗る）
- **使うもの**: 凍結版のパネルに対する Elo。パネルのレートは ratings/ratings.json の BT 値に**固定して当て直さない**
  （`scripts/rating.py` は追加のたびに全員を当て直す。レーティング表としては正しいが、学習曲線の物差しが動く）。
  書き出し1つの Elo はパネルの各相手との勝敗から1次元の最尤で出す（`speedlab.fit_fixed`）
  - 一つのレートは当てはまりがよくない（全ペアの BT の χ²/df ≈ 9.8、rl_deduce_v4 は当てる相手で 1573〜1771）。
    **絶対値はパネル込みで意味を持つ**ので、腕どうしの比較は同じパネル・同じ局の**ペア差**で行う
  - パネルは測る範囲の上下 ±250 Elo 以内から、系統（同じ系列・近い祖先・特化系・古い本線）を混ぜて選ぶ
- **共通乱数**: 手の乱数を「相手ごとの seed・局番号・その局の何番目の手番か」だけで決める（`speedlab.keyed_actions`）。
  2つの書き出しが同じ手を選ぶ限り同じ局面が続くので、ペア差の分散が減る。以前の評価はバッチ分の乱数をまとめて引いていたので、
  どこかの局で反則が起きるだけで全局の乱数がずれていた
- **GPU では学習ループの中で回せる**（凍結版は同じ形のネットなので `OpponentPool` でまとめて推論できる）。768局の自己対局が約5秒なので、
  段階の区切りで 16,000局（Elo の標準誤差 約3）を測っても1段階 8時間に対して約2分

**本番規模の検出力**（ペアにした局の得点差の標準偏差 0.50 から）:

| 検出したい差 | 0.5pt | 1.0pt | 1.5pt | 2.0pt | 3.0pt |
| --- | --- | --- | --- | --- | --- |
| 要るペアの数（有意水準 5%・検出力 80%） | 78,500 | 19,600 | 8,700 | 4,900 | 2,200 |

直近の段階の伸びは +0.1〜+2.7pt なので、**1段階を2倍速くする方法（+1.1pt 前後）でも、今の CI のガントレット（約5,000組）では
検出力 34%**。本番規模の A/B は「速そうなものを確かめる」場所で、ふるい分けは安い代理で行う。
同じ設定を seed だけ変えた run どうしのばらつきは本番規模ではまだ測っていない（arm 1 と arm 3 の差が +0.4〜+0.8 だったことから
0.8pt 以下と見込まれる）。最初の A/B で対照を2本回して測っておくと、以後の判定が楽になる。

## 3. 段階を分けた比較

| 段 | どこで | 何を | 費用 |
| --- | --- | --- | --- |
| 0 | CPU（このコンテナでも可） | **学習なしの診断**: 勾配の分散・雑音のスケール（`rnad/gradsnr.py`）、数式を変えない高速化の一致（テスト） | 数分〜数十分 |
| 1 | CPU | **代理の学習曲線**（`rnad/speedlab.py`）。小さいネット・64局/更新・200〜300更新を、腕ごとに seed 2〜3本 | 1 run 約1時間 |
| 1.5 | GPU | 模倣ネットからのやり直し（最初の 2,000更新は伸びが急なので、1.5倍速い方法なら 2,000〜4,000組で見える） | 1腕 3〜5時間 |
| 2 | GPU（本番） | 最新の checkpoint から1段階（Δm = 2,000更新）の A/B。対照は2本 | 1腕 約8時間 |
| 3 | CI | 凍結版ガントレット＋歩哨（estimator_v14）＋ rl_search の A/B（非推移性の見張り） | |

**代理は2つ作って、1つは使えなかった**:
- **P1（ゼロから）は使えない**: 乱数初期化の 32ch×3 を 64局/更新・学習率 2e-4 で 90更新（5,760局）回しても、乱数方策への勝率が
  0.436 → 0.471 → 0.504 → 0.486（256局ずつ、±6pt）で横ばいだった。ほぼ全局が反則10回で終わる「反則を覚える」段階で、
  本線の後半（鋭い方策・中盤の信用割り当て）とは律速がまったく違う。初期の方策はほぼ一様なので、4節で述べるスパイクも起きない
- **P2（蒸留した出発点）**: rl_deduce_v4 を 32ch×3 の小さいネットへ蒸留し（2,048局・16.9万決定点、12エポック、
  検証で最善手の一致 86%）、そこから R-NaD を続ける。生徒は rl_v23 に 53%・rl_v25 に 45%・rl_v28 に 70%・rl_v30 に 76%
  （64局ずつ。step 0 のパネル評価 128局では 58 / 52 / 68 / 77%）で、固定パネルの Elo は 1602（パネル最上位の rl_v30 1553 より上、
  ratings.json では rl_selfplay_v1〜v2 くらい）。**パネルに生徒より強い相手がいない**点は弱み（上が詰まると伸びが見えにくい。
  次に作るなら rl_selfplay_v2 前後の相手を足す）。方策が鋭いので本線と同じスパイクの状況になる（6.2）。
  設定は 64局/更新・学習率 1e-4・Δm = 100・ターゲットの平均化 0.02（本線の Δm / ターゲットの時定数 = 2,000 / 1,000 の比を保つ）・
  β = 16・η = 0.2。パネルは rl_v23 / rl_v25 / rl_v28 / rl_v30（レートは ratings.json に固定）
- 代理の答えは「ふるい」で、判定ではない。代理で強く効いたものだけを段 1.5〜2 で確かめる。逆に代理で効かなかったものは、
  効かなかった理由が代理の都合（短さ・小ささ）かどうかを見てから捨てる

## 4. 学習なしの診断（本線の rl_deduce_v4、CPU）

自己対局した局を、そのネットを現在・ターゲット・正則化方策の全部に使って（= 段階の頭、η の項は消える）R-NaD の損失にかけ、
局ごとの勾配を求めた（`rnad/gradsnr.py`、384局・32,346決定点）。

| 変種 | 局ごとの勾配の分散 trΣ（参照比） |
| --- | --- |
| 参照（NeuRD のクリップ 10,000） | 1（1.46×10⁶。期待勾配の大きさ \|G\|² ≈ 163 だが誤差（約170）の内なので、B_noise ≈ 9,000局は下限の目安。半分ずつに分けた内積で推定すると \|G\|² ≈ 83・B_noise ≈ 17,600局） |
| クリップ 1,000 | 0.148 |
| クリップ 300 | 0.045 |
| クリップ 100 | 0.015 |
| クリップ 30 | 0.005 |
| 1/μ の上限 100 | 0.015 |
| 1/μ の上限 30 | 0.005 |

- s の絶対値は中央値 1.1・99% 点 88・最大 10万。**上位 0.1% の決定点が s² の 99.6%** を占める。選ばれた手の μ は中央値 0.88、
  1% 点 0.009（方策が鋭いほど、まれな手が選ばれたときの 1/μ が大きい）
- 別の計測（512局）では μ < 0.001 の決定点（全体の 0.27%）が s² の 99.9% を持ち、そのアドバンテージの平均は −0.06 ± 0.08（ほぼ 0）、
  反則率 23%（全体 12%）。rl_v15・rl_v20・rl_selfplay_v1 でも同じ集中（99.5〜99.95%）で、**本線の最初からずっと払っている税**であり、
  最近の伸びの鈍化の原因ではない
- **分かったこと・分からなかったこと**: クリップや上限で分散は 1/7〜1/200 に減る。一方、どの変種でも期待勾配の大きさは 384局では
  誤差より小さく（参照でも 163 ± 約170）、**クリップで向きがどれだけずれるか（偏り）は学習なしでは測れなかった**。
  雑音のスケールが数千局あるので、向きを測るには数万局が要る。偏りの影響は学習を回して（代理 P2・本番の A/B で）見るしかない
- Adam は1次モーメントなし（β1 = 0）なので、各パラメータの1歩は「勾配 / √(2次モーメント)」で、2次モーメントはスパイクで決まる。
  別の計測で、スパイクを除くと幹の1歩が中央値で 14倍（クリップ 100）〜29倍（クリップ 20）大きくなる見込み

## 5. 実装したもの（tsuitate-nn ブランチ `claude/admiring-carson-1hwun6`、どれも既定は従来と同じ）

**A. 数式を変えない（またはほぼ変えない）高速化** — 学習曲線の取り直しは要らず、基準機で秒を測って採否を決める

| フラグ | 中身 | 確かめたこと | 見込み（RTX 3070、768局） |
| --- | --- | --- | --- |
| `--packed` | 方策の計算を合法手（平均 約80手、最大 約360手）に詰めて行い、正則化方策の対数確率を1回目から2回目へ持ち越す。2回目の prev / prev_ の順伝播と [決定点, 11,259] の要素演算がなくなる（1標本あたりの順伝播 9 → 7回分） | 従来の更新と損失・全パラメータの勾配が一致（相対差 1e-6、`tests/test_packed.py`） | 更新 9.4秒 → 約7秒 |
| （常に有効） | α が 0 / 1 のとき、重みが 0 の正則化ネットを順伝播しない（段階の後半は α = 1） | 混ぜた値とビット単位で同じ | 平均 −0.5回分の順伝播 |
| `--pipeline` | 自己対局を別スレッド（CUDA では優先度の高い別ストリーム）で集め、更新と重ねる。batch は1更新前の方策で集めたもの（v-trace の重要度比が補正する。1更新あたりの KL は、本線の 250更新ごとの KL 0.0003〜0.0005 を酔歩として割って約1e-6 の見込み）。**自己対局だけ・ボーナスなし・補助ヘッドなしに限る**（`--league` / `--guard` / `--speed` / `--nyugyoku` / `--aux-truth` と併用すると止まる） | 動作と再現性（専用の乱数列。同じ `--seed` なら同じ run）。CPU の値（7.1 の 1.57倍）は GPU には移らないので、壁時計の効きは基準機で測る | 1更新 = 「自己対局 + 更新」→「大きいほう」 |
| `--compact-legal` | batch の合法手のマスクを密な bool でなく添字で持つ（768局で 0.79GB → 11MB）。`--pipeline` で batch が2つ同時にあるときの WSL2 のメモリ（既定 8GB）対策 | 密なマスクと損失・勾配が一致 | 速さはほぼ同じ |

3つを合わせて 1更新 14.9秒 → **約8〜8.5秒（約1.8倍）**の見込み（スループット担当の見積もり。基準機での確認は 7節の手順）。

**B. 1標本あたりの効きを変えるもの**（学習曲線で比べる）

| フラグ | 中身 | ねらい・注意 |
| --- | --- | --- |
| `--inv-mu-cap K` | v-trace の s に掛かる 1/μ を K で頭打ちにする（価値の目標には効かない） | 4節のスパイクを取る。確率 1/K 未満の手だけに効き、そこでは NeuRD の押し出しが K × 方策勾配 になる。**偏り**: 価値の目標がずれている（δ = v − V）局面で、まれな手を (1 − Kμ)δ だけ押す（NeuRD の「基準をずらしても同じ」性質が崩れる）。K ≥ 100 が安全側 |
| `--neurd-clip C` | NeuRD のアドバンテージのクリップ（参照 10,000） | 同じねらい。報酬の尺度に依存するので、スタイル特化（報酬 > 1）では `--inv-mu-cap` のほうが扱いやすい |
| `--policy-loss pg` | NeuRD の押し出しに各手の π を掛ける（η = 0・π = μ のときソフトマックス方策勾配と一致することをテストで確認） | 1/μ が消える。代わりに **確率の低い手への押し出しが消える**（NeuRD が直そうとした、決定的な誤りが固まる性質）。本線に入れる前に、方策の固まり方（下の見張り）と混合戦略の保ち方を確かめる |
| `--target-avg` / `--extra-ema` | ターゲットの平均化係数 / 学習に使わない追加の平均（書き出しだけ） | 雑音の多い領域では書き出しを平均するほど強くなりうる（代わりに遅れる）。`--extra-ema` は学習に影響しないので本線でもすぐ付けられる |
| `--c-vtrace` | v-trace の c（1 未満で λ-return） | 優先度は低い（分散の大半は 1/μ で、λ では減らない） |
| `--adam-b1` / `--reuse` | Adam の1次モーメント / 1つの batch で複数回更新 | 優先度は低い（モーメンタムは長期の拡散を変えない。使い回しは雑音の多い領域では学習率を上げるのと同じで、後半で効いたのは学習率を下げるほう） |

**C. 測る道具**

| ファイル | 中身 |
| --- | --- |
| `rnad/speedlab.py` | `panel`（パネルを総当たりで作る。`--fix <名前>=<値>` の1体だけを固定し、残りは総当たりから当てる。CPU で回り、スレッド数は `OMP_NUM_THREADS`〔無ければ 1〕）/ `eval`（run の書き出しをパネルで測る。局ごとの結果を残す）/ `report`（腕ごとの学習曲線・予算の終わり・対照との局ごとのペア差）。ratings.json のレートを全員に固定するパネル（P2 のもの）は、`planes` / `members` / `ratings` を持つ JSON を手で書く |
| `train_rnad.py --panel` | 学習ループの中で固定パネルを測り、`panel_eval.jsonl` へ（speedlab report の入力と同じ形）。GPU なら安い |
| `rnad/gradsnr.py` | 学習なしの診断: 変種ごとの局ごとの勾配の分散・期待勾配・雑音のスケール |
| `rnad/bench_update.py` | 1更新の壁時計（従来 / packed / 連続 / 重ねる）と、packed の勾配・更新量の一致（`grad_rel_err_max` / `grad_cos_min` / `delta_cos_min`。`--compact-legal` は持たない） |
| `rnad/distill.py` | 方策ネットを小さいネットへ蒸留する（代理 P2 の出発点） |
| `--reset-adam` / `--lr-warmup N` | 途中から更新の式を変える A/B で、両腕の Adam の状態を捨てて温め直す（下の注意） |
| 学習ログの `pi_top_mean` / `pi_top_gt_0999` / `entropy_mean` | 方策が決定的に固まっていないかの見張り（PG や 1/μ の上限で先に動く） |

**途中から更新の式を変える A/B の注意（重要）**: checkpoint の Adam の2次モーメントは、今の式の勾配（スパイク）の大きさを
b2 = 0.999 で何千更新も覚えている。分散を減らす腕へ切り替えると、実効の学習率が 1/μ の上限 100 で最初 0.07倍・
半分に戻るまで約4,200更新、PG では約8,000更新ほぼ止まる見込み。そのまま比べると「更新の式の違い + 学習率が 5〜14分の1」の
比較になる。**両腕に `--reset-adam --lr-warmup 100` を付ける**（対照も同じ条件にそろえる）。

## 6. 試した結果（CPU）

### 6.1 偏り: クーンポーカーで厳密な搾取されやすさを見る（`rnad/toy_kuhn.py`）

学習なしの診断では偏り（向きのずれ）が測れなかったので、厳密な NashConv（各プレイヤーの最善応答の価値の和、0 = ナッシュ均衡）が
計算できるクーンポーカーで、**本物の `RNaDLearner`**（v-trace・NeuRD・β = 16・正則化方策の差し替え）をそのまま回した。
ネットは情報集合 12 個の表。参照が収束する設定（学習率 1e-2・512局/更新・Δm = 500・ターゲット 0.01）で 6,000更新、seed 3本。
β = 16 なので方策は鋭くなり（最小の手の確率 1e-5 前後）、1/μ のスパイクも起きる。

| 変種 | 後半 3,000更新の NashConv（ターゲット、seed 平均） | 参照比 |
| --- | --- | --- |
| 参照（NeuRD） | 0.0163 ± 0.0009 | — |
| 1/μ の上限 100 | 0.0165 ± 0.0010 | 同じ |
| NeuRD のクリップ 100 | 0.0167 ± 0.0010 | 同じ |
| PG 型の損失 | 0.0176 ± 0.0007 | +8% |
| 1/μ の上限 20 | 0.0194 ± 0.0012 | +19% |
| 1/μ の上限 5 | 0.0277 ± 0.0009 | +70% |

- 上限は強くするほど混合均衡への収束を遅らせる（上限 5 は後半 3,000更新の平均で参照の約1.7倍の NashConv。6,000更新の時点では
  0.0147 対 0.0129 で約1.1倍まで縮むが、参照も 5,000更新の 0.0070 から振れて上がっている）が、**K = 100 は参照と区別できない**。
  本線の推奨値（K ≥ 100）の偏りの心配は、この大きさのゲームでは見えなかった
- PG は少し遅い（+8%）が、混合を失って固まることはなかった（2行動のゲームなので「確率の低い手の押し出しが消える」害は出にくい。
  本線の 60手前後から選ぶ局面では強く出うる）
- 注意: 12情報集合・2行動のゲームなので、本線の大きい行動空間での偏りの大きさまでは言えない

### 6.2 代理 P2 は本線と同じ「スパイク」の状況か

蒸留した生徒（P2 の出発点）を 4節と同じ診断にかけた（384局・32,764決定点）: s の上位 0.1% の決定点が s² の **99.6%**（本線 99.6〜99.9%）、
局ごとの勾配の分散は本線の約10倍。1/μ の上限 100 で分散は 0.5%、PG で 0.001% まで減り、**上限 100 では期待勾配が推定できる**
（|G|² = 70、雑音のスケール 約1,080局。参照では推定できない）。P2 は本線と同じ状況を（より強く）再現している。

### 6.3 代理 P2 の学習曲線

設定は 3節の P2（64局/更新・Δm = 100・ターゲット 0.02・β = 16・η = 0.2・200更新）。パネルは rl_v23 / rl_v25 / rl_v28 / rl_v30
（レートは ratings.json に固定）、各書き出しを相手1体あたり 128局（計 512局、1点の標準誤差 約15〜20 Elo）で測った。
対照とのペア差は同じ seed・同じ相手・同じ局番号の得点差（共通乱数）。

**学習率 1e-4（本線と同じ）: どの腕も出発点（1602）から動かない**（seed 1）

| 腕 | 50 | 100 | 150 | 200 | 対照との局ごとのペア差（50〜200 更新の合算） |
| --- | --- | --- | --- | --- | --- |
| 対照 | 1579 | 1581 | 1605 | 1590 | — |
| 1/μ の上限 100 | 1589 | 1610 | 1607 | 1586 | +1.2 ± 1.3pt |
| 1/μ の上限 20 | 1595 | 1601 | 1607 | 1602 | +1.7 ± 1.3pt |
| PG | 1584 | 1615 | 1589 | 1604 | +1.2 ± 1.3pt |

64局 × 200更新 = 12,800局では、出発点（小さいネットへの蒸留で先生より弱い）からの伸びが評価の誤差に埋もれる。

**学習率を上げると、対照は雑音で壊れ、1/μ の上限 100 は壊れ方がずっと小さい**（seed 1。学習率 3e-4 では出発点のまま、
1e-3 では上限 100 も出発点から −40〜−50 Elo 下がる）

| run | 50 | 100 | 150 | 200 |
| --- | --- | --- | --- | --- |
| 対照・学習率 1e-4 | 1579 | 1581 | 1605 | 1590 |
| 対照・学習率 3e-4 | 1597 | 1565 | 1575 | **1548** |
| 対照・学習率 1e-3 | 1499 | 1430 | 1463 | **1477** |
| 1/μ の上限 100・学習率 3e-4 | 1599 | 1600 | 1600 | **1593** |
| 1/μ の上限 100・学習率 1e-3 | 1497 | 1548 | 1567 | **1552** |
| PG・学習率 3e-4 | 1593 | 1600 | 1608 | **1602** |

- 学習率 3e-4 での上限 100 − 対照: 200更新で **+6.2 ± 2.8pt**、50〜200更新の合算で +3.6 ± 1.4pt（局ごとのペア差、seed 1本）
- 学習率 1e-3 での上限 100 − 対照: 100〜200更新で +16.5 / +14.7 / +10.7pt（各 ±3.0）、合算 **+10.4 ± 1.5pt**。どちらも 50更新で
  一度下がる（新しい Adam の最初の数十更新が大きく動く）が、上限 100 はそこから戻り、対照は戻らない
- PG（学習率 3e-4）も壊れない（1602）。PG も 1/μ を消すので、上限 100 と同じ側に入る（PG は 3e-4 だけで確認）
- 見張りの指標も同じ向き: 対照はエントロピーが上がり（学習率 3e-4 で 0.71 → 約0.79。1e-3 では最初の 50更新で 0.96 前後まで
  跳ねてから 0.85 前後）、価値の損失は学習率 1e-3 で 1.8 から最大 約11（10更新平均、81〜90更新）まで崩れる（200更新では約3まで戻る）。
  上限 100 は学習率 3e-4 でエントロピー 0.73〜0.76・価値の損失 約1.78 のまま（学習率 1e-3 では上限 100 も最初の数更新で
  価値の損失が 17.8 まで跳ね、エントロピーは 0.80 前後）
- **読み**: 雑音（まれな手の 1/μ）が方策を平らに溶かし、学習率を上げるほど壊れる。上限はそれを止める。ただし**まだどの腕も
  出発点より強くなっていない**ので、ここで言えるのは「大きい学習率でも壊れにくい」までで、「速く強くなる」とはまだ言えない

**代理の妥当性確認（既知の失敗の再現）**: β = 2（本線では模倣ネットからの R-NaD で現在のネットが 300更新で錨に 23% まで
弱くなった設定）を P2 で回すと、100更新で 1602 → 1473（50） → 1457（100）と崩れ、エントロピーが 0.68 → 1.22 に上がった
（方策が平らに潰れる、本線と同じ壊れ方）。P2 は既知の悪化を検出できる。

**seed 2 での確認**（学習率 3e-4、2 seed）: 200更新で対照 1551 ± 3・上限 100 1595 ± 2、同じ seed どうしの Elo の差 **+44 ± 1**、
局ごとのペア差 +6.0pt（2 seed とも +6）。ただし seed 2 で差が出たのは 200更新（対照が落ちた点）だけで、50〜150更新は ±1pt 以内。
50〜200更新の合算は 2 seed で +2.5 ± 1.1pt（Elo の差の平均 +15 ± 7）。

**バッチ 128（雑音で律速されているかの確かめ）**: 学習率 1e-4 のまま 1更新 128局にしても、200更新で 1584（対照 64局は 1590）で、
**1更新あたりの伸びは良くならなかった**。P2 のこの予算では「データを増やせば速くなる」領域にいない（そもそも出発点から伸びていない）。

### 6.4 書き出しの平均化

P2 の各 run で、学習に使わない追加の平均（`--extra-ema 0.005,0.1`。ターゲットは 0.02）を同じ更新数で測った
（13 run × 100/200更新 = 25点。標準誤差は run ごとに平均してから、run の間のばらつきで出す）:

| 比べたもの | Elo の差（平均 ± 標準誤差） |
| --- | --- |
| ターゲット − 現在のネット | +25.2 ± 7.0 |
| 長い平均（0.005）− ターゲット | +10.6 ± 5.3 |
| 短い平均（0.1）− ターゲット | −7.6 ± 3.3 |

平均を長くするほど書き出しが強く見えるが、**差のほとんどは出発点から大きく下がった run（β = 2・学習率 1e-3・学習率 3e-4 の対照）
から来ている**。それ以外の8 run では、長い平均 − ターゲットが +3.0 ± 2.1、短い平均 − ターゲットが −2.6 ± 2.4 でどちらも誤差の内
（ターゲット − 現在は +9.9 ± 3.8）。つまり「出発点に近いから強い」効果と分けられていない（200更新でも長い平均は出発点の重みを
約37%残し、追加の平均は学習の頭のネット = 出発点から始まる）。P2 からは平均化の効き目は言えない。
本線では学習に影響しない（`--extra-ema 0.0003,0.003 --tail-avg --export-current`）ので、付けて段階の区切りで比べるのが安い。

## 7. GPU（ゲーム用 PC）で回す手順

### 7.1 次の Δm の区切りで: 数式を変えない高速化（学習曲線の A/B は要らない）

1. tsuitate-nn をブランチ `claude/admiring-carson-1hwun6` にする（Rust 側・rl-env は変えていないので入れ直しは要らない）
2. 学習済みの checkpoint で30分ほど測る（学習を止めている間に。乱数初期化のネットは局が長く遅く出る）:
   ```sh
   .venv/bin/python rnad/bench_update.py --ckpt out_rnad/selfplay_v2planes/checkpoint.pt --batch 768 --reps 3 --loop 6
   ```
   - `packed` の**勾配**の相対誤差（`grad_rel_err_max`）が 1e-5 以下なら数式は同じ。CPU・rl_deduce_v4 の重みでは 5e-7〜1e-6 だった
     （数式の一致そのものは `tests/test_packed.py` が CPU で検査している）。GPU の既定の精度（畳み込みは TF32）での値は未計測で、
     丸めの差で 1e-5 を超えうる。超えたら `grad_cos_min` を見る（L4 で fp32 と tf32 の更新量のコサインが 0.9996 だったので、
     同じ精度どうしの packed はそれより十分 1 に近いはず。float32 なので 1 をわずかに超えて出ることがある）。更新量のコサイン
     `delta_cos_min` は、Adam の状態が新しいと1歩目が勾配の符号に近いので 0.9994 程度まで下がる（本物の checkpoint では 1 に近いはずだが未計測）
   - 参考: CPU（このコンテナ、rl_deduce_v4 と同じ 64ch×6・16局）では更新 9.0秒 → packed 6.6秒（1.36倍）、
     「自己対局 + 更新」11.3秒 → 重ねて 7.2秒（1.57倍）。GPU では比が変わるので必ず基準機で測る
   - 最後の行の「重ねる …（従来比 N倍）」（JSON では (`collect_sec` + `update_sec`) / `pipelined_sec`）が 1.4倍以上なら採用。
     メモリ: bench_update は `--compact-legal` を持たず、`pipelined` の段は密なマスクの batch を2つ持つ（768局で約1.4GB 多い）ので、
     学習の設定より大きく出る。7GB を超えても即不採用にせず、採用後の最初の数十更新で学習のプロセスのピーク（タスクマネージャ /
     `free -h`）が 7GB 未満かを見る。batch の観測（fp16、768局で約0.9GB）は `--compact-legal` でも減らないので、2つ同時で約1.8GB は残る
3. 採用なら、次の段階から `--packed --pipeline --compact-legal` を足して再開する（設定の上書きは要らない。
   どれも checkpoint の設定に入らない）。合わせて**学習に影響しない**次の3つも付ける:
   `--extra-ema 0.0003,0.003 --export-current --tail-avg`（書き出しの平均化を比べるため。6.4・8節の2）
4. 学習ログの `ratio_dev_mean`（`--pipeline` で1更新遅れの方策で集めた分の |π/μ − 1| の平均）が 1e-3 前後であること
   （1更新の KL 約1e-6 の見込みに相当。`--pipeline` なしでは数値誤差だけで、L4 の tf32 で最大 2.6e-6）。`ratio_dev_max` は1更新の
   約6万決定点の最大でまれな手ほど大きく出るので、判定に使わない（CPU の代理〔rl_deduce_v4・学習率 1e-4・16局/更新・Adam は
   30更新ぶん〕でも最大 0.08〜0.24・平均 0.006〜0.013。本物の Adam の状態では小さいはずだが、基準機では未計測）。平均が 1e-2 を
   超え続ける、または `loss_v` / `entropy_mean` / `pi_top_mean` が `--pipeline` を入れる前の段階の推移から外れるなら、`--pipeline` を外して比べる

#### 7.1 の実測（2026-10-21、RTX 3070・WSL2）

deduce 系統の `checkpoint_68000.pt`（rl_deduce_v5、64ch×6・91枚）・768局/更新・`--precision tf32`。学習を止めている間に測った。

**`bench_update.py --batch 768 --reps 3 --loop 6`**: 自己対局 6.36秒 + 更新 7.47秒 = 13.83秒、packed の更新 5.57秒（1.34倍）、
連続 12.17秒、重ねる 9.43秒（従来比 1.47倍）。packed の勾配のコサイン 0.99999994〜1.00000012・更新量のコサイン 1.000000。
勾配の相対誤差は最大 5.6e-5 で 1e-5 を超えたが、コサインはほぼ 1 なので TF32 の丸めの差と見る（上の手順の 2 の注記どおり）。

**本物の学習**（68,000 のコピーから本線と同じ設定〔`run_deduce_s10000.sh`〕で回し、更新ごとのログの中央値・平均）:

| 設定 | 更新回数 | 1更新 | `loss_v` | `ratio_dev_mean` | ピーク（WSL の RAM / GPU） |
| --- | --- | --- | --- | --- | --- |
| 従来 | 40 | 約15.2秒（自己対局 6.2 + 更新 9.1） | 1.78 | 1.0e-4 | 6.8GB / 2.4GB |
| `--packed --compact-legal` | 15 | 約13.5秒（自己対局 7.2 + 更新 6.3） | 1.79 | 1.1e-4 | 5.0GB / 1.9GB |
| `--packed --pipeline --compact-legal` | 40 | 約8.7秒（待ち 1.4 + 更新 7.3） | **約1.0** | **1.9e-2** | 6.2GB / 2.2GB |

- **`--packed --compact-legal` は従来と同じ学習**（`loss_v`・`ratio_dev_mean`・`entropy_mean` が一致）。速さは約1.1倍で、
  bench の 1.34倍より小さい（この run だけ自己対局が 1秒ほど遅く出た。ばらつきかは切り分けていない）。メモリは減る
- **`--pipeline` は学習信号を変える**。最初の1更新（普通に集めた batch）は従来と一致し、重ねて集めた2更新目から `loss_v` が
  1.78 → 0.8〜1.2、`ratio_dev_mean` が 1e-4 → 0.011〜0.028 に跳んだ（見込みの 1e-3 の約20倍、手順 4 の警戒線 1e-2 も超える）。
  1更新で方策が動く量は、250更新ごとの KL を酔歩として割った見込みよりずっと大きい（1更新の動きの多くは次の更新で打ち消し
  合うので、長い区間の KL から1更新の大きさは見積もれない）。v-trace の c = min(1, π/μ) が約75手の局で掛け合わされて縮み、
  価値の目標が実際の結果よりネット自身の v に寄る。`loss_v` が下がったのはそのためで、良くなったのではない。
  ここで扱いを「数式を変えない高速化」から「**学習曲線の A/B が要る腕**」に移す（約1.7倍なので、同じ秒数で勝てるなら価値は大きい）
- 従来の run では1回だけ、自己対局の1回に 941秒かかった（PC の利用か WSL の一時停止と思われる。平均から外した）
- ログはゲーム用 PC の WSL `~/speedtest_logs/`

**手軽な A/B（2026-10-22）**: 本線の段階（68,000 → 78,000、`--packed --compact-legal`）を対照にして、同じ 68,000 から
`--packed --pipeline --compact-legal` の腕を 70,000 まで回し（約5時間）、70,000 どうしを比べた。

| 指標（68,000 → 70,000） | `--pipeline` の腕 | 対照（本線） |
| --- | --- | --- |
| 直接対戦 1,000局（run 39724961182、`match_seed=20260930`） | **50.8%±3.1**（505-489-6） | — |
| 錨 rl_deduce_v4 への勝率（50更新ごと・40回の合計） | 60.0% | 59.5% |
| `entropy_mean` / `pi_top_mean` / `pi_top_gt_0999` | 0.548〜0.553 / 0.808〜0.810 / 0.268〜0.272 | 0.548〜0.552 / 0.809〜0.810 / 0.270〜0.271 |
| 1更新 | **8.5秒** | 13.3秒 |

3pt を超える悪化は無い（2,000更新ぶんの差なので、小さな差の積み重ねまでは見えない）。約1.56倍速いので、**78,000 からの段階に
`--pipeline` も入れる**（ユーザー判断）。区切りごとのアリーナで前の版との差を見て、伸びが前の段階よりはっきり落ちたら外して確かめる。
重みは Release `rlw-deduce-pipeline-ab-s70000-20261022` / `rlw-deduce-s10000-s70000-20261022`

### 7.2 1回だけ: 同じ設定の複製の対照（seed 間のばらつきを測る）

どの A/B の検出力の計算にも効く一番大きい未知数。本線と同じ checkpoint をコピーし（7.3 と同じ手順）、本線のその段階と**同じ引数**
（7.1 で足した `--packed --pipeline --compact-legal` などを含む）に **`--reseed --seed <別の値>`** を足して、`--steps <checkpoint の step + 2000>`
で1段階回す。`--pipeline` なしでは自己対局の乱数が checkpoint の乱数状態から続くので、`--reseed` を付けないと `--seed` を変えても
同じ自己対局が再生され、ばらつきが 0 に見える。`--pipeline` ありでは自己対局の乱数を `--seed` と step から作る（`PipelinedCollector`）ので、
効くのは `--seed` を変えることのほう（`--reseed` は付けても害はない）。
本線の同じ段階の書き出しとのペア差（CI のガントレット、`match_seed`）が、同じ設定の run どうしのばらつきになる。

### 7.3 分散を減らす腕の A/B（代理 P2 で効いたら）

```sh
# 対照も腕も、同じ checkpoint のコピーから。両腕に --reset-adam --lr-warmup 100（5節の注意）
# train_rnad.py は <out>/checkpoint.pt を上書きするだけで、step ごとの checkpoint は残さない。
# 本線を区切り（例 --steps 58000）で止めた直後の checkpoint.pt をコピーし、step を確かめる
mkdir -p out_rnad/ab_ctrl out_rnad/ab_cap100
cp out_rnad/selfplay_v2planes/checkpoint.pt out_rnad/ab_ctrl/checkpoint.pt
cp out_rnad/selfplay_v2planes/checkpoint.pt out_rnad/ab_cap100/checkpoint.pt
.venv/bin/python -c "import torch; print(torch.load('out_rnad/ab_ctrl/checkpoint.pt', map_location='cpu')['step'])"  # 区切りの step（例 58000）
# --steps は通しの更新回数（58,000 から 2段階 = 4,000更新なら 62000）
.venv/bin/python -u rnad/train_rnad.py --out out_rnad/ab_ctrl   --steps 62000 <本線と同じ引数> --reset-adam --lr-warmup 100 \
    --packed --pipeline --compact-legal --export-current --extra-ema 0.0003,0.003 --tail-avg --panel panel_v1.json --panel-every 500 --panel-games 2048
.venv/bin/python -u rnad/train_rnad.py --out out_rnad/ab_cap100 --steps 62000 <本線と同じ引数> --reset-adam --lr-warmup 100 \
    --packed --pipeline --compact-legal --export-current --extra-ema 0.0003,0.003 --tail-avg --panel panel_v1.json --panel-every 500 --panel-games 2048 \
    --inv-mu-cap 100 --override-config
```

- **途中で止めて再開するときは `--reset-adam --lr-warmup 100` を外す**（どちらもその実行の頭で効くので、付けたまま再開すると
  Adam の状態をもう一度捨て、学習率を 0 から上げ直す）。`--inv-mu-cap 100` は最初の実行で checkpoint の設定に入るので、
  再開に `--override-config` は要らない
- 集計: `.venv/bin/python rnad/speedlab.py report out_rnad/ab_ctrl out_rnad/ab_cap100 --panel panel_v1.json --control ab_ctrl --which target`
  （`--panel-which` の既定は target、report の `--which` の既定は current なので、付けないと表が空になる）。読むのは step ごとの Elo の表と
  対照とのペア差。要約の「平均 Elo（曲線下の面積）」と「1更新の秒」は step 0 から始まる run を前提にしていて、58,000 から再開した run では
  使えない。ペア差の「step > 0 の全体」にも、両腕で同じ重みの起点（58,000）が差 0 で入る
- **2段階（4,000更新）を見る**: 1段階目の差は「水準」、2段階目の差が「速さ」。直近の変更（学習率 1e-4、768局、確定事実のプレーン）は
  どれも「1回だけ上がって、次の段階から横ばい」だったので、水準の上乗せと速さを分けて読む
- 判定はパネル（学習ループ内、区切りで 16,000局まで増やせる）と CI のガントレットのペア差。直接対戦（B 対 A）は感度が高いが
  自分の系列への特化を含むので、ペア差と並べて読む
- 見張り: 学習ログの `pi_top_gt_0999`（0.999 を超える決定点の割合）が対照より 5pt 以上増える・`entropy_mean` が 2割以上減るなら、
  方策が決定的に固まり始めている（1/μ の上限・PG で NeuRD の性質が弱まった兆候）。rl_search の価値ヘッドへの影響は、
  固定パネルの局で価値の較正（最終結果に対する Brier）を見る（道具は未実装。`panel_eval.jsonl` は局の結果だけで価値の予測を
  持たないので、見るなら speedlab に足す）
- パネル `panel_v1.json`（例）: 同じ系列 rl_selfplay_v2 / rl_selfplay_v4 / rl_deduce_v2 / rl_deduce_v4、近い祖先 rl_v29 / rl_v30、

### 7.4 浮いた時間の使い方（高速化を入れた後で）

同じ基準機の秒数で次の2つを比べる（両腕 `--reset-adam --lr-warmup 100`。5節の注意）: (i) `--batch 1536`・学習率 1e-4、
(ii) 768局・2倍の更新回数・`--lr 5e-5 --override-config`（学習率は checkpoint の設定に入っているので上書きが要る。`--batch` は入って
いないので要らない）。`--steps` は通しの更新回数なので、(i) は起点 + N、(ii) は起点 + 2N。正則化の段階（`--schedule`）は更新回数で
数えるので、(ii) は同じ秒数で (i) の2倍の段階を進む（局数でそろえるなら (ii) を `--schedule 4000 --override-config` にする）。
(i) は batch が倍で、`--pipeline` では観測だけで約1.8GB × 2 になるのでメモリを見る。
Adam（β1 = 0）は1歩が局数によらずほぼ学習率で決まるので、局数と学習率は一緒に動かす。これは「雑音で律速されているか」の
確かめにもなる（局数を倍にしても1更新あたりの伸びが変わらないなら、分散を減らす手も効かない）。

**CPU の代理で分かること・分からないこと**: このコンテナの予算（1 run 約1.3万局）では、本線の水準の方策をさらに強くする量の学習は
起きない（P2 の対照は 200更新で出発点から動かない）。代理で確かめられるのは (1) 数式の一致、(2) 雑音の減り方（学習なしの診断）、
(3) **壊れにくさ**（大きい学習率・β = 2 のような既知の失敗を再現・回避するか）、(4) 偏り（小さいゲームの厳密な NashConv）まで。
「速く強くなるか」そのものは GPU の A/B（段 1.5〜2）でしか測れない。
