# 学習の速さの比較と、速く強くなる学習方法の実験（2026-10-20）

> 種類: 設計/記録。状態: **比較方法の提案と、CPU での診断・代理実験の結果**。本線（ゲーム用 PC の R-NaD）は止めずに、
> 別の計算資源で「同じ計算量でより強くなる学習方法」を探すための物差しと、その最初の試行。
> 学習側のコードは tsuitate-nn のブランチ `claude/admiring-carson-1hwun6`（**どれも既定は従来と同じ**。本線の再開に影響しない）。
> 計測はクラウドの CPU 4コア（GPU なし）。本線と同じ規模の学習は回せないので、学習なしの診断と小さい代理で測った。

## 要点

1. **本線は「勾配の雑音」で律速されている**（学習なしの診断、rl_deduce_v4）。1局ごとの勾配の分散に対して期待勾配が小さく、
   雑音のスケール B_noise（勾配の向きが雑音に埋もれない局数）は **約9,000局**で、1更新の 768局よりずっと大きい。
   段階ごとの伸びが縮み、段階の中で KL が酔歩のように線形に伸び続ける、という本線の観察と合う
2. **その雑音のほとんどは「まれにしか選ばれない手」から来る**。v-trace の s = (結果 − v)/μ の2乗和の **99.6〜99.9% を、
   確率 μ < 0.001 の手が選ばれた 0.1〜0.3% の決定点**が占める（その手の平均のアドバンテージはほぼ 0）。NeuRD のクリップ 10,000 は
   事実上効いておらず、本家は β=2 で方策を混合のまま保って 1/μ を間接的に抑えていたが、β=16 の本線には抑えが無い。
   このスパイクが Adam の2次モーメントを幹全体で決めてしまい、価値の損失・正則化の引きのほうは幹にほとんど届かない
   （幹の Adam の v に占める割合: s の項 100%、価値 5×10⁻⁶、正則化 7×10⁻⁵）
3. **数式を変えない高速化で 1更新 14.9秒 → 約8秒の見込み**（合法手に詰めた更新・重み 0 の正則化ネットの省略・
   自己対局と更新の重ね合わせ。どれも実装済みで既定オフ。GPU での確認が残る）
4. **比較の物差し**: 学習中の錨や直前の版との直接対戦は使わない（直前の版との直接対戦は、直近7段階で進歩を約4.5倍に見せていた）。
   固定パネル（凍結版、レートは ratings.json に固定）に対する Elo を、更新回数・決定点数・基準機の秒数の関数として並べる。
   本番規模の1段階 A/B は「2倍速い」方法でも検出力が約3割しかないので、**安い代理でふるい、GPU では少数を確かめる**
5. 代理実験の結果は 6節（P2: rl_deduce_v4 を小さいネットへ蒸留した出発点から、分散を減らす腕を比べた）

## 1. 何を「速さ」とするか

**強さ（固定パネルの Elo）を計算量の関数として**並べ、同じ Elo に届くまでの計算量の比（速度比 M）で比べる。
横軸は3つ取り、どこで速くなったかを分ける:

| 横軸 | 何が分かるか |
| --- | --- |
| 更新回数 | 1更新あたりの賢さ（アルゴリズム） |
| 決定点数（標本数） | 1標本あたりの効き（分散を減らす手・標本の使い回し）。局数より決定点数（局の長さは学習で 117手 → 60手台まで縮む） |
| **基準機の秒数（主）** | ゲーム用 PC（RTX 3070）での壁時計。律速の資源はこの PC の時間なので、最終的にはこれで比べる |

- 基準機の秒数は **CPU で測った壁時計を使わない**（このコンテナでは同じ設定でも負荷で 1更新 13〜280秒に振れた）。
  ゲーム用 PC の実測からのコストモデル（1更新 ≈ 0.9秒 + 5ms × 局数 + 0.134ms × 決定点数 × 順伝播の回数/9）で換算し、
  重ね合わせ（`--pipeline`）のようにモデルが当てはまらない変更は基準機で直接測る（`rnad/bench_update.py`）
- 数式を変えない高速化（下の 5節の A 群）は学習曲線を取り直す必要がない: 勾配の一致をテストで確かめ、基準機で1更新の秒を測るだけ
- 要約: (a) 速度比 M（対照の伸びの 25〜90% の範囲の Elo で、同じ Elo に届く計算量の比の幾何平均）、(b) 予算の終わりの Elo
  （同じ計算量で）、(c) log(計算量) で平均した Elo。標準誤差は**学習の seed の間のばらつき**から出す（同じ run の書き出しどうしは
  相関するので独立に数えない）

## 2. 物差し: 固定パネルの Elo

- **使わないもの**:
  - 学習中の錨への勝率（run ごとに錨が違い比べられない。錨が弱くなると 88〜95% で頭打ちする）
  - **直前の版との直接対戦**。直近7段階（46,000〜58,000更新）で、直接対戦から換算した伸びの合計は +475 Elo だが、
    全パネルの BT では +105、別系統どうしの対局だけで当て直すと +44（自分の系列への特化が乗る）
- **使うもの**: 凍結版のパネルに対する Elo。パネルのレートは ratings/ratings.json の BT 値に**固定して当て直さない**
  （`scripts/rating.py` は追加のたびに全員を当て直す。レーティング表としては正しいが、学習曲線の物差しが動く）。
  書き出し1つの Elo はパネルの各相手との勝敗から1次元の最尤で出す（`speedlab.fit_fixed`）
  - 一つのレートは当てはまりがよくない（全ペアの BT の χ²/df ≈ 9.8、rl_deduce_v4 は当てる相手で 1573〜1771）。
    **絶対値はパネル込みで意味を持つ**ので、腕どうしの比較は同じパネル・同じ局の**ペア差**で行う
  - パネルは測る範囲の上下 ±250 Elo 以内から、系統（同じ系列・近い祖先・特化系・古い本線）を混ぜて選ぶ
- **共通乱数**: 手の乱数を「相手ごとの seed・局番号・その局の何番目の手番か」だけで決める（`speedlab.keyed_actions`）。
  2つの書き出しが同じ手を選ぶ限り同じ局面が続くので、ペア差の分散が減る。以前の評価はバッチ分の乱数をまとめて引いていたので、
  どこかの局で反則が起きるだけで全局の乱数がずれていた
- **GPU では学習ループの中で回せる**（凍結版は同じ形のネットなので `OpponentPool` でまとめて推論できる）。768局の自己対局が約5秒なので、
  段階の区切りで 16,000局（Elo の標準誤差 約3）を測っても1段階 8時間に対して約2分

**本番規模の検出力**（ペアにした局の得点差の標準偏差 0.50 から）:

| 検出したい差 | 0.5pt | 1.0pt | 1.5pt | 2.0pt | 3.0pt |
| --- | --- | --- | --- | --- | --- |
| 要るペアの数（有意水準 5%・検出力 80%） | 78,500 | 19,600 | 8,700 | 4,900 | 2,200 |

直近の段階の伸びは +0.1〜+2.7pt なので、**1段階を2倍速くする方法（+1.1pt 前後）でも、今の CI のガントレット（約5,000組）では
検出力 34%**。本番規模の A/B は「速そうなものを確かめる」場所で、ふるい分けは安い代理で行う。
同じ設定を seed だけ変えた run どうしのばらつきは本番規模ではまだ測っていない（arm 1 と arm 3 の差が +0.4〜+0.8 だったことから
0.8pt 以下と見込まれる）。最初の A/B で対照を2本回して測っておくと、以後の判定が楽になる。

## 3. 段階を分けた比較

| 段 | どこで | 何を | 費用 |
| --- | --- | --- | --- |
| 0 | CPU（このコンテナでも可） | **学習なしの診断**: 勾配の分散・雑音のスケール（`rnad/gradsnr.py`）、数式を変えない高速化の一致（テスト） | 数分〜数十分 |
| 1 | CPU | **代理の学習曲線**（`rnad/speedlab.py`）。小さいネット・64局/更新・200〜300更新を、腕ごとに seed 2〜3本 | 1 run 約1時間 |
| 1.5 | GPU | 模倣ネットからのやり直し（最初の 2,000更新は伸びが急なので、1.5倍速い方法なら 2,000〜4,000組で見える） | 1腕 3〜5時間 |
| 2 | GPU（本番） | 最新の checkpoint から1段階（Δm = 2,000更新）の A/B。対照は2本 | 1腕 約8時間 |
| 3 | CI | 凍結版ガントレット＋歩哨（estimator_v14）＋ rl_search の A/B（非推移性の見張り） | |

**代理は2つ作って、1つは使えなかった**:
- **P1（ゼロから）は使えない**: 乱数初期化の 32ch×3 を 64局/更新・学習率 2e-4 で 90更新（5,760局）回しても、乱数方策への勝率が
  0.436 → 0.471 → 0.504 → 0.486（256局ずつ、±6pt）で横ばいだった。ほぼ全局が反則10回で終わる「反則を覚える」段階で、
  本線の後半（鋭い方策・中盤の信用割り当て）とは律速がまったく違う。初期の方策はほぼ一様なので、2節で述べるスパイクも起きない
- **P2（蒸留した出発点）**: rl_deduce_v4 を 32ch×3 の小さいネットへ蒸留し（2,048局・16.9万決定点、12エポック、
  検証で最善手の一致 86%）、そこから R-NaD を続ける。生徒は rl_v23 に 53%・rl_v25 に 45%・rl_v28 に 70%・rl_v30 に 76%
  （64局ずつ）と中堅の凍結版くらいの強さで、方策が鋭いので本線と同じスパイクの状況になる。
  設定は 64局/更新・学習率 1e-4・Δm = 100・ターゲットの平均化 0.02（本線の Δm / ターゲットの時定数 = 2,000 / 1,000 の比を保つ）・
  β = 16・η = 0.2。パネルは rl_v23 / rl_v25 / rl_v28 / rl_v30（レートは ratings.json に固定）
- 代理の答えは「ふるい」で、判定ではない。代理で強く効いたものだけを段 1.5〜2 で確かめる。逆に代理で効かなかったものは、
  効かなかった理由が代理の都合（短さ・小ささ）かどうかを見てから捨てる

## 4. 学習なしの診断（本線の rl_deduce_v4、CPU）

自己対局した局を、そのネットを現在・ターゲット・正則化方策の全部に使って（= 段階の頭、η の項は消える）R-NaD の損失にかけ、
局ごとの勾配を求めた（`rnad/gradsnr.py`、384局・32,346決定点）。

| 変種 | 局ごとの勾配の分散 trΣ（参照比） |
| --- | --- |
| 参照（NeuRD のクリップ 10,000） | 1（1.46×10⁶。期待勾配の大きさ \|G\|² ≈ 163 で B_noise ≈ 9,000局） |
| クリップ 1,000 | 0.148 |
| クリップ 300 | 0.045 |
| クリップ 100 | 0.015 |
| クリップ 30 | 0.005 |
| 1/μ の上限 100 | 0.015 |
| 1/μ の上限 30 | 0.005 |

- s の絶対値は中央値 1.1・99% 点 88・最大 10万。**上位 0.1% の決定点が s² の 99.6%** を占める。選ばれた手の μ は中央値 0.88、
  1% 点 0.009（方策が鋭いほど、まれな手が選ばれたときの 1/μ が大きい）
- 別の計測（512局）では μ < 0.001 の決定点（全体の 0.27%）が s² の 99.9% を持ち、そのアドバンテージの平均は −0.06 ± 0.08（ほぼ 0）、
  反則率 23%（全体 12%）。rl_v15・rl_v20・rl_selfplay_v1 でも同じ集中（99.5〜99.95%）で、**本線の最初からずっと払っている税**であり、
  最近の伸びの鈍化の原因ではない
- **分かったこと・分からなかったこと**: クリップや上限で分散は 1/7〜1/200 に減る。一方、どの変種でも期待勾配の大きさは 384局では
  誤差より小さく（参照でも 163 ± 約170）、**クリップで向きがどれだけずれるか（偏り）は学習なしでは測れなかった**。
  雑音のスケールが数千局あるので、向きを測るには数万局が要る。偏りの影響は学習を回して（代理 P2・本番の A/B で）見るしかない
- Adam は1次モーメントなし（β1 = 0）なので、各パラメータの1歩は「勾配 / √(2次モーメント)」で、2次モーメントはスパイクで決まる。
  別の計測で、スパイクを除くと幹の1歩が中央値で 14倍（クリップ 100）〜29倍（クリップ 20）大きくなる見込み
