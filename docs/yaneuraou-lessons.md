# やねうら王から取り込めるもの／取り込めないもの（2026-07-26 調査）

調査対象: https://github.com/yaneurao/YaneuraOu
（HEAD `0899d1d`, 2026-07-25。`source/` 約29k行 + `engine/`・`eval/`・`mate/`・`book/`）

## 結論（先に要約）

やねうら王は**完全情報**の将棋エンジンなので、ついたて将棋の最大のギャップ
（反則経済 31pt = 粒子の信念の質、docs/improvement-plan-2026-07-25.md 参照）には
**直接効く部品がない**。粒子フィルタ・観測尤度・演繹に相当する層が向こうには存在しない。

一方で、次の2つの層は丸ごと学べる。

**(1) 評価関数の手作り項**（→ 第1章）。`eval/material/evaluate_material.cpp` に
「駒得のみ」から1項目ずつ足していく連載版評価関数が Lv1〜Lv9 として全部残っており、
**各段階に Elo の実測値が付いている**。利き・駒の連結・玉周辺の穴が、どの順で
どれだけ効くかがそのまま読める。ついたて側の `evaluate()` は**利きをすべて
「あり/なし」の二値**で扱っていて（`shogi.rs::is_attacked` が bool を返す）、
利き数・玉からの距離重み・予防的な紐が丸ごと抜けている。

**(2) 計算資源の配分**（→ 第2章）。現状の tsuitate-bot は

- 1手あたりの思考予算が**固定**（`TSUITATE_THINK_BUDGET_MS`、`strategy.rs:272`）で、
  残り時間（`view.clocks`）を**一切見ていない**
- 候補評価が「全候補 stage1 → 上位 `depth2_top_k=8` だけ stage2」の**固定2段**
  （`strategy.rs:1389-1502`）で、時間が余っても深くならず、足りなくても浅くならない

## 0. 前提: 構造的な差の整理

取り込みを検討する前に、何が対応して何が対応しないかを固定しておく。

| やねうら王 | ついたて将棋での対応物 | 備考 |
|---|---|---|
| 局面 `Position` | 粒子1個 | 粒子は具体的なフル局面なので1:1で対応する |
| 探索木のノード | （なし） | 相手手が観測でしか分からないので木が張れない。2手読みが限界 |
| 静的評価 `evaluate()` | `strategy.rs::evaluate()` の粒子加重平均 | 「1局面の評価」ではなく「分布上の期待値」 |
| 置換表（局面キー） | 粒子指紋 | 既に `estimator` がユニーク化に使っている |
| 合法手 | 候補手（合法性はサーバーのみが知る） | ここが最大の差。`p_legal` という次元が向こうには無い |
| 詰み判定 | 粒子ごとの詰み判定 → 確率 | 「詰み」が二値でなく確率になる |

つまり **「1局面に対する操作」はほぼ全部そのまま粒子に対して使える**が、
**「木を掘る」系の技術（LMR・futility・null move・aspiration・ProbCut）は
土台ごと無い**。以下ではこの区別に沿って選別する。

## 1. 評価関数: 利きと駒の連結

> 以下の小節は**やねうら王側で効いた大きさの順**に並べている。
> ついたてに実装するときの推奨順序は依存関係が別にあるので、第5章を見ること
> （V4 → V1 → V3 → V2。V4 が最も安く、V2 が最も高い）。

### 1-0. 元ネタ: 「評価関数を作ってみよう」連載（Lv1〜Lv9）

`source/eval/material/evaluate_material.cpp`（909行）に、**駒得だけの評価関数から
1項目ずつ足していく教材版**が `MATERIAL_LEVEL` 1〜9 として全部残っている。
各段階のコメントに Elo の実測値が付いているのが極めて有用:

| Lv | 追加した項目 | 効果 |
|---|---|---|
| 1 | 駒得のみ | （これでも R2300 あると書かれている） |
| 2 | **盤上の駒はその価値の 1/10 を減点**（`:61` `score -= piece_value * 104/1024`） | +R50 |
| 3 | **盤上の全マスの利きを、玉からの距離に反比例する価値で評価**（`:75-125`） | **+R200** |
| 4 | 1マスに複数の利きがある時、価値は**指数関数的に逓減**（`:140-155`） | +R30 |
| 5-6 | テーブル一本化（KKPEE9）。高速化であって評価内容の追加ではない | +R70 |
| 7 | **駒に味方の利きがあれば加点（紐）／相手の利きがあれば減点（質）**（`:432-434`, `:475-485`） | +R25 |
| 8 | **玉の8近傍に「玉以外の味方の利きが無い」マスを減点**（`:607-624`）＋玉の位置ボーナス（`:574-584`） | +R65 |
| 9 | 利きの価値を**方角ごと**に変える（`:786-791`） | +R50 |

読みどころは Lv3 の重み設計（`:75-89`）で、コメントに**optimizer が出した実測値**が
そのまま残っている:

```
our_effect_value   = { 1024, 496, 297, 272, 184, 166, 146, 116, 117 }  // 自分の利き
their_effect_value = { 1024, 504, 357, 320, 220, 194, 160, 136, 130 }  // 相手の利き
```

配列の添字は**玉からの距離**。ここから3つ読み取れる:

1. **距離1で価値がほぼ半分**になる。実装の近似式 `83×1024/(d+1)` より実測は急峻
2. `their > our` が全距離で一貫している。すなわち
   **「自玉の近くに相手の利きがある」減点のほうが「自分の利きがある」加点より重い**
3. 複数利きの逓減（`:154`）は `6365 - 0.8525^(m-1) × 5341`。
   利き1本を1.0とすると 2本目で1.76、3本目で2.25、…と**明確に逓減するが飽和はしない**

**ついたて側との一致**: `EvalParams` の既定値は `attack_w=0.0434` / `pressure_w=0.0918`
（`strategy.rs:635-636`）で、**自玉への圧力を相手玉への圧力の約2.1倍重く見ている**。
やねうら王の非対称性（1.1〜1.2倍）と符号が一致していて、SPSA が独立に同じ構造を
見つけている。これは以下の提案の信頼性を上げる材料になる。

### 1-1. ついたて側の現状（何が無いか）

`strategy.rs` / `value_features.rs` を読んだ結果、**利きに関する量がすべて二値**だった。

| やねうら王の量 | ついたて側 | 実体 |
|---|---|---|
| そのマスの利きの**数**（0〜10、KKPEEでは0/1/2に圧縮） | **無し（bool）** | `shogi.rs:308` `is_attacked()` は最初の1枚で `return true` |
| 玉からの距離で重み付けした利きの総和 | **無し** | `king_zone_pressure`（`strategy.rs:2915-2932`）は玉の**隣接9マスのうち攻撃されているマス数**を数えるだけ。距離の重みも利き数もない |
| 全マスの利き価値 | ほぼ死んでいる | `coverage_after`（`:351-376`）は自駒の被覆マス数を**平等に**数えるだけ。`coverage_w` は SPSA の結果 **0.0013**（実質ゼロ） |
| 全駒の紐/質（味方・相手の利き） | **攻撃されている駒のみ** | `recapture_risk`（`:2788-2798`）は `is_attacked(to, opp)` が偽なら 0 を返す。`exposed_capture_risk` も同様 |
| 自玉8近傍の「味方の利きが無い穴」 | **無し** | 相手の利き（`pressure`）と相手の持ち駒による打ち込み面積（`drop_check_danger`）は見ているが、**自分の守りの穴**は見ていない |

value ネット側（`value_features.rs:142-167` の20次元）も同じで、
`king_zone_pressure` の二値カウントが入っているだけ。**利き数は特徴量にも無い**ので、
「NN が学習で吸収しているはず」という言い訳が立たない。

### 1-2. V2: 利きの価値を玉からの距離で重み付ける（最優先）

**根拠**: 連載中で最大の伸び（Lv2→Lv3 で +R200）。

**ついたて側の状況が示唆すること**: `coverage_w` が SPSA でほぼゼロ（0.0013）に
潰されたのは、**「全マス平等に利き被覆マス数を数える」量に情報が無かった**からだ、
という解釈ができる。やねうら王の知見は「利きの価値は玉からの距離に強く依存する」
なので、**同じ利き情報でも重み付けを変えれば生き返る可能性がある**。

**提案**: `coverage_after` を、単純なマス数から

```
Σ_マス  (自分の利き数の価値) × w_our[dist(マス, 自玉)]
      + (自分の利き数の価値) × w_their[dist(マス, 相手玉)]
```

に置き換える。ついたて特有の扱いは:

- **自玉の位置は完全既知**なので、自玉からの距離での重み付けは**ノイズゼロ**で計算できる
- **相手玉の位置は粒子の信念**。粒子ごとに玉位置が具体的なので、
  粒子加重平均すれば自然に「玉位置の不確かさで薄まった攻め圧力」になる。
  `blind_king_attack`（既存のブラインド玉攻めボーナス）の一般化にあたる
- 相手の利きは見えないので、`w_their` 側（相手の利きの評価）は粒子上でのみ計算する

**罠**: 全マス×利き走査は重い。**E（利きの差分計算）を先にやるか、同時にやる**。
これを素直に書くと `pressure_samples=16` どころではないコストになる。

**検証**: `coverage_w` を距離重み版に差し替えたうえで、
SPSA の `TUNE_PARAMS` マスクで新しい重みだけを調整 → 200局ガントレット。
「元の `coverage_w` をゼロにしただけの版」も並べて、**距離重みが効いているのか
単にノイズが減っただけなのか**を切り分けること。

### 1-3. V1: 利きの「数」を数える

**根拠**: Lv4 で +R30。ただし V2/V3 の前提でもある（利き数がないと逓減も紐の強弱も表現できない）。

**提案**: `is_attacked(sq, by) -> bool` の隣に `attack_count(sq, by) -> u8` を作る
（早期 return をやめて数え上げる）。そのうえで

- `recapture_risk` / `exposed_capture_risk` の「紐つき割引」を、
  **攻め駒の数 vs 守り駒の数**で決める。現状は `defended` が真なら一律
  `recapture_defended=0.4692` を掛けるだけで、**2枚で狙われて1枚で守っている駒**と
  **1枚で狙われて1枚で守っている駒**が同じ評価になっている
- `king_zone_pressure` を「攻撃されているマス数」から「利き数の合計（逓減つき）」へ

**ついたてでの意味**: 相手の利き数は粒子ごとにしか分からないが、
**自分の守りの利き数は完全既知**。つまり「守り枚数」は正確に、
「攻め枚数」は粒子加重で、という非対称な扱いになる。
`bin/analyze` が数えている「只取られ」「損な交換」は、まさにこの枚数勘定の
失敗が主因である可能性が高い（現状は枚数を数えていないので原理的に取りこぼす）。

**逓減の形**: やねうら王の実測（1本=1.0, 2本=1.76, 3本=2.25, …）をそのまま
初期値に使い、SPSA で調整する。

### 1-4. V3: 予防的な紐（連結）

**根拠**: Lv7、+R25。全盤上駒に対して
「味方の利きがあれば駒価値の +0.8%／+1.0%（1枚／2枚）」
「相手の利きがあれば駒価値の −2.8%／−3.0%」を加える（`:433-434`, `:483-484`）。

**ついたて側**: 現状の紐は**すでに攻撃されている駒にしか効かない**。
つまり「まだ狙われていないが紐をつけておく」手に価値が付かない。

**ついたてでは将棋よりこの項の価値が高いはずだ、という理屈**:

> 将棋では「狙われてから紐をつける」で間に合うことが多い。ついたてでは
> **相手の攻めが見えない**ので、狙われたことに気づけない。事前に紐が
> ついている駒は、気づかないまま只取られされる確率がそもそも低い。

これは `bin/analyze` の「只取られ」の直接の対策になりうる。しかも
**自駒同士の連結は完全既知情報**なので、粒子を使わずに計算できる（＝安い・ノイズなし）。

**罠**: 加点係数の絶対値が小さい（駒価値の1%）ことに注意。
やねうら王でも紐は +R10 程度で、**質（相手の利き）の減点のほうが3倍重い**。
ついたてでは相手の利きが見えないので、質の側は粒子経由になり精度が落ちる。
**紐（既知・安い）だけ先に入れて測る**のが筋が良い。

### 1-5. V4: 自玉8近傍の「味方の利きが無い穴」

**根拠**: Lv8、玉8近傍で「玉以外の味方の利きが無い」マスについて、
そこが空きか敵駒なら減点、味方の駒があるなら加点（`:607-624`）。+R35。

**ついたてで特に相性が良い理由**: この量は**自分の駒だけで計算できる**。
相手の駒が見えなくても、「自玉の隣接8マスのうち、自分の利きが1枚も無いマスが何個あるか」は
**完全に既知**。粒子もいらない。`board.rs`（自駒だけを考慮した候補手生成）の情報だけで足りる。

現状の `hand_drop_w`（相手の持ち駒による打ち込み王手の受け入れ面積）は
**相手の持ち駒**という別の既知情報から同種の危険を測っている。V4 はその対になる項で、
**両方あって初めて「打ち込まれる面積 × 支えの無さ」が表現できる**。
`mate.rs` の被詰めろ（`mate_risk_w`）とも素直に噛み合う
（打ち一手詰めが成立する条件は、まさに「玉の近傍に支えの無い空きマスがある」）。

**優先度が高い理由**: 既知情報だけ・粒子不要・計算が軽い。**費用対効果が最も良い**。

### 1-6. V5: 盤上の駒は価値を1割引く

**根拠**: Lv2、単独で +R50。`score -= piece_value × 104/1024`（`:61`）。
含意は「同じ駒なら持ち駒のほうが価値が高い」。

**ついたて側**: `exchange_value(role) = (盤上価値 + 持ち駒価値)/2`（`strategy.rs:345-347`）は
**交換時の価値**の話で、保有形態による差ではない。盤上の駒と持ち駒を同一視している。

**ついたてでは持ち駒の優位がさらに大きいはずの理屈**: 持ち駒は
(a) 相手から見えない、(b) 任意のマスに打てる（＝索敵ユニットにもなる）。
`tokin_probe_w=0.2025` が既に「歩を打って成る」に価値を認めているのは、この一部。

**ただし逆向きの力もある**: 打ちマスの反則が反則原因の最多（270件）。
持ち駒は「打てるマスが分からない」というついたて固有のコストを負う。
**どちらが勝つかは実測でしか分からない**ので、係数の符号を固定せず
SPSA の範囲を正負にまたがらせて調整するのが良い。

### 1-7. V6: 玉の位置評価（符号が逆になる可能性あり）

やねうら王の `king_pos_bonus`（`:574-584`）は、1段目・端寄りが高い
（＝囲いに入っている玉が良い）。**ついたてではこれがそのまま使えるとは限らない**:

- 相手は自玉の位置を知らない。`deduce::opp_king_candidates` の鏡像で、
  **相手も同じ演繹をしてくる**（初期位置の玉は推測されやすい）
- 一方で `big_home_penalty`（大駒が初期位置に残ることへの減点）は
  「初期位置は予測可能だから悪い」という論理で既に入っている。
  **同じ論理を玉に適用すべきかは未検証**

つまり V6 は「テーブルを移植する」話ではなく、**ついたて用のテーブルを実測で作る**話。
`bin/analyze` の対局記録から「玉がどのマスにいた局面の勝率が高いか」を集計すれば
初期値は作れる。優先度は中。

### 1-8. 方法論として学ぶこと

この連載でいちばん価値があるのは、個々の項目そのものより**進め方**かもしれない。

- **1項目ずつ足して、そのつど Elo を測る**。9段階すべてに数字が付いている
- **効く順序の相場観**: 利きの評価（+R200）＞ 盤上駒の減価（+R50）≒ 方角別（+R50）
  ＞ 玉周辺の穴（+R65 の内訳は +R15/+R20/+R30）＞ 複数利きの逓減（+R30）＞ 紐（+R25）。
  **「利きをどう評価するか」が単独で他の全部を合わせたより大きい**
- **最初は手で係数を決め、後から optimizer に回す**。Lv3 のコメントには
  手で決めた `83×1024/(d+1)` と optimizer の答えが**両方**残っていて、
  近似式が実測とどうズレたかが読める

ついたて側の開発規律（1変更1測定・200局ガントレット・match_seed ペア比較）は
既にこれと同型なので、**そのまま適用できる**。

## 2. 探索・計算資源の配分（優先度順）

### A. 残り時間に応じた思考予算配分（TimeManagement）

**やねうら王側**: `source/timeman.cpp` の `TimeManagement::init_()`（194-308行）。

- 残り手数の見積り `MTG`（`MoveHorizon=160` から手数を引く。切れ負けなら+40、
  40手目までは大きめに見る = 序盤は勝負どころでないので節約する）
- `optimum = minimumTime + 残り時間/MTG`、
  `maximum = minimumTime + 残り時間 × max_ratio / MTG`（`max_ratio=5.0`、
  ただし**残り時間の30%を超えない**）
- 秒読み・切れ負け・フィッシャーで別扱い。ネットワーク遅延を先に引く
  （`NetworkDelay`=120ms、切れ負け直前用に `NetworkDelay2`=+1000ms）
- ふかうら王（MCTS側）はさらに手数係数を掛ける（`dlshogi_searcher.cpp:771-785`）:
  20手目まで1.5、〜30手3.5、〜40手4.0、以降3.0。序盤は時間を使っても
  良い手にならないので削る、という明示的な設計判断

**ついたて側の現状**: `strategy.rs:272` の `think_budget_ms()` が環境変数を読むだけで、
毎手同じ予算。本番（300秒+3秒）へは `TSUITATE_THINK_BUDGET_MS` を一律に絞って
収めている（CLAUDE.md）。**`view.clocks`（`protocol.rs:64-70` の
`sente_ms`/`gote_ms`）は届いているのに使っていない**。

**提案**:

1. `SearchBudget::from_ms()`（`strategy.rs:281-312`）の入力を、固定値ではなく
   `clocks` から計算した値にする。式はやねうら王をそのまま使わず、
   ついたて用に単純化して始める:
   - `MTG` = 残り手数の見積り（ついたては反則で手番が変わらないので、
     **1手番あたり平均何回 choose() が呼ばれるか**を掛ける必要がある。
     ここが将棋との実質的な差。records/analyze の反則回数統計から係数を出せる）
   - `optimum = 残り時間/MTG + increment`、`maximum = min(optimum×3, 残り×0.3)`
2. 手数係数（序盤は薄く、中終盤に厚く）を入れる。ついたては序盤の情報量が
   将棋よりさらに少ない（相手が全く見えない）ので、**序盤の削りは将棋より
   攻めて良い**という仮説が立つ。これは実測で決める話。

**検証**: アリーナは既にフィッシャー時計をシミュレートして `PlayerView.clocks` に
実際の残り時間を流している（`selfplay.rs:125-140`, `:180-181`）ので、**戦略側の
変更だけで検証できる**。ただし `FISCHER_INITIAL_MS`/`FISCHER_INCREMENT_MS` は
定数（`selfplay.rs:33-34`）なので、**本番相当の 300秒+3秒 で回せるよう env で
上書きできるようにする**のが前提作業。

- 合格条件: 300秒+3秒条件で、固定予算版に 200局で有意勝ち越し
- 罠: 「時間を使い切って引き分けが増える」変質。`bin/analyze` の終局理由と
  思考時間統計（平均/p99/最大）を必ず併記する。時間切れ負けは即失格

**期待効果**: 現状「本番では予算を絞る＝弱くする」しかない構造が、
「勝負どころに配る」に変わる。棋力そのものは上がっていないが、
**同じ持ち時間から取り出せる棋力が上がる**。凍結版との比較で素直に測れる。

### B. 早期打ち切りと不安定時の延長

**やねうら王側**: 2系統ある。

1. **αβ側**（`yaneuraou-search.cpp:1969-1996`）— 反復深化のたびに
   `totalTime = optimum × fallingEval × reduction × bestMoveInstability` を
   再計算する。`bestMoveInstability = 1.04 + 1.8956 × 最善手が変わった回数`。
   **最善手が揺れている局面ほど時間を伸ばす**。逆に読み筋が安定していれば縮める
   （`timeReduction`）。評価値が下がり続けているとき（`fallingEval`）も伸ばす
2. **MCTS側**（`dlshogi_searcher.cpp:851-959`）— より直接的で、ついたてに近い:
   - `rest_maximum_po` = nps × 残り時間 = 「あと何回サンプルできるか」を推定
   - 1位の訪問数が2位 + `rest_maximum_po × ratio` を超えていたら、
     **残り時間を全部2位に注ぎ込んでも逆転しないので打ち切る**（early exit）。
     `ratio` は勝率差に応じて縮む（差0.2で0）
   - 「1位が2位の1.5倍以上訪問されていて、かつ勝率も上回る」が安定条件
   - 逆転しないと分かったら諦めて打ち切る（retirement）分岐も別にある

**ついたて側の現状**: `choose()` は全候補を stage1、上位8を stage2 で評価して
終わり。**スコア差が開いていようが接戦だろうが同じ計算量**を使う。

**提案**: MCTS側の考え方をそのまま持ち込める。ついたてでの対応は

- 「訪問数」→ **その候補の評価に使った粒子数**
- 「勝率差」→ 候補間の `score` 差
- `rest_maximum_po` → 残り予算で追加評価できる粒子数

として、
1. stage1 のスコア差が十分開いていれば、stage2 を上位2〜3手だけで打ち切って
   **残り時間を次の手に繰り越す**（A と組み合わせて初めて意味がある）
2. 逆に上位が接戦（差が乱数タイブレーク幅 `0.01` 程度に埋もれている）なら、
   **その候補群にだけ粒子を追加して評価し直す**

「粒子を増やしたら1位が入れ替わったか」は `bestMoveChanges` の直接の対応物になる。
これは A の延長判断にも使える。

**罠**: 候補間のスコア差は `p_legal` で割り引かれた合成値なので、
差が小さい＝どちらでも良い、とは限らない（反則確率が拮抗しているだけの場合がある）。
打ち切り判定には `gain` と `p_legal` を分けて見るべき。

### C. 段階的な候補展開（MovePicker のステージ化）

**やねうら王側**: `movepick.h:42-143` / `movepick.cpp:462-690`。
指し手を一度に全部生成・評価せず、
`TT手 → 好捕獲 → キラー/好quiet → 悪捕獲 → 悪quiet` の**段階**で、
**必要になるまで生成すらしない**。βカットが起きればそこで打ち切る。
スコアリング（`movepick.cpp:264-460`）も種類ごとに別式で、捕獲は MVV+captureHistory、
quiet は history 各種の和 + 王手ボーナス、王手回避は捕獲に `1<<28` の下駄を履かせる。

**ついたて側の現状と、これが刺さる理由**: `strategy.rs:1479-1502` の
`depth2 = i < budget.depth2_top_k`（既定8）は**固定の足切り**。
docs/improvement-plan-2026-07-25.md の項目2 が挙げている
「自駒 en-prise 逃げが上位8に入らず 2手読みの恩恵を受けずに沈む」疑いは、
まさにこの構造の問題。

**提案**: `depth2_top_k` を定数ではなく**時間で決める**（progressive widening）。

```
上位から順に stage2 へ流し、予算が尽きるか、
「残り候補の stage1 スコア上限 < 現1位の stage2 スコア」になったら止める
```

stage1 スコアは stage2 の上界ではないので厳密な枝刈りにはならないが、
`depth2_replace × risk_mean` の可動域は有界なので**保守的な上界は作れる**
（`gain2 = gain + depth2_replace × (risk_mean + delta)` の `delta` の範囲を見積もる）。
これで「時間が余っていれば9番目以降も見る」「足りなければ3手で止める」が両立する。

**罠**: 「上位8を16にする」だけの単純拡大は既に予算スケール（`with_scale`）で
できるので、**それとの差分**を測らないと意味がない。比較対象は
「同じ壁時計で top_k 固定 vs 適応」であって「top_k 8 vs 16」ではない。

### D. 詰み探索の拡張

**やねうら王側**:

- `mate_1ply`（`mate/mate1ply_with_effect.cpp` 他）— 近接王手に限定した高速1手詰め。
  「漏れがある代わりに極めて速い」と明記されている（`mate.h:21-26`）。
  **ついたての `mate.rs` が打ちに限定しているのと同じ思想**
- `weak_mate_3ply`（`mate/mate.cpp:25-118`）— 「利きのある場所への取れない近接王手
  からの3手詰め」。条件が秀逸で、**王手の移動先に自分の利きがあり、相手の利きが
  玉以外に無い**マスだけを試す。逆王手が出たら即諦める。全合法手を掘らずに
  3手詰めの実用的な部分集合だけ取る
- `check_squares(pt)`（`position.h:532`）— 駒種ごとの「そこに置けば王手になるマス」を
  局面更新時に前計算しておく。これがあるので**王手生成 `MoveList<CHECKS>` が安い**

**ついたて側の現状**: `mate.rs` は打ち限定（冒頭コメントに理由が明記されている:
費用と頻度。実測で被詰めろの72%が打ち詰み）。残り28%は取りこぼしている。

**提案**:

1. 粒子ごとに `check_squares` 相当（玉位置から逆引きした「王手になる (マス,駒種)」）を
   持てば、**盤上駒の移動による王手も安く列挙できる**。`mate.rs::drop_check_candidates`
   は既に玉から8方向を走査して逆引きしているので、**同じ走査で「そのマスへ利いている
   自駒」を拾えば移動王手に拡張できる**（追加コストは小さい）
2. `weak_mate_3ply` の条件（取れない近接王手＝自分の利きがあり相手の利きが玉だけ）は、
   ついたてでは「**攻め側は自分の支え駒を正確に知っている**」ので素直に使える。
   `mate.rs` の `MateThreat::{Mate, IfSupported}` の2段階と相性が良い

**ただし最優先ではない理由**: 詰めろ2項（`mate_threat_w`/`mate_risk_w`）は
**アリーナ中立〜悪化で既定 0 に据え置き中**（メモリ: mate-terms-arena-neutral-2026-07-25）。
検出率を上げても w=0 なら何も変わらない。**先に「検出漏れが実害を出しているか」を
`bin/analyze` の被詰めろオラクルで測る**こと。打ち以外の詰みで実際に負けている
局面が少ないなら、この項目は着手しない。

### E. 差分計算（利き・特徴量）

**やねうら王側**:

- `extra/long_effect.h` — 各マスの利き数を**盤面更新時に差分で維持**する
  （`LONG_EFFECT_LIBRARY`）。`weak_mate_3ply` が `board_effect[us].effect(to) >= 2`
  のように O(1) で利き数を引けるのはこれのおかげ
- `eval/nnue/nnue_feature_transformer.h:553-600` — NNUE の accumulator。
  `refresh_accumulator`（全計算）と `update_accumulator`（差分）を持ち、
  1手進むごとに**変化した特徴量インデックスだけ**加減算する
  （`AppendChangedIndices`）。玉が動いたときだけ全計算に落とす
  （`kRefreshTrigger`）

**ついたて側の現状**: `NN_SAMPLES = 48` のコメント（`strategy.rs:317-320`）に
「forward pass 自体は 0.6µs だが、**transition 特徴量の利き走査が粒子×候補ごとに
掛かる**ため粒子数を絞る」と明記されている。`PRESSURE_SAMPLES = 16` も同じ理由。
**つまり評価粒子数のボトルネックは NN ではなく利き走査**。

**提案**: `shogi.rs::Position` に利き数ボード（先後×81マスの u8）を持たせ、
`do_move` 相当で差分更新する。粒子は候補手ごとに1手進めて評価するので、
**「1手ぶんの差分」が正確に効く形**になっている。

- 期待効果: `nn_samples` / `pressure_samples` / `mate_samples` の上限が上がる
  = 同じ予算でより多くの粒子を評価できる = 評価分散が下がる
- 検証: まず `cargo bench` 相当（無ければ `bin/rank_probe` の壁時計）で
  利き走査の実コストを測ってから着手する。**測らずにやらない**
- 罠: 差分更新はバグると静かに壊れる。`shogi.rs` は perft で検証されているので、
  **同じ要領で「全計算と差分計算が一致する」プロパティテスト**を必ず付ける

**注意**: `estimator` は既に `IncrementalEstimator`（scenario-gui 用）で
「作り直しと差分更新が一致する」テストを持っている。同じ設計規律をここにも適用する。

### F. value ネットの入力設計（HalfKP / HalfKPE9）

**やねうら王側**: `eval/nnue/features/half_kpe9.h:19-40`。
特徴量 HalfKPE9 = **(玉の位置) × (玉以外の駒の位置) × (先後の利き数 3×3通り)** の
巨大スパース one-hot。次元数は `SQ_NB × fe_end × 9`。
同時に1になるインデックスは駒数ぶんだけなので、accumulator 差分と噛み合う。

**ついたて側の現状**: `value_features.rs` は **手作りスカラー**
（v10 凍結時点で state16 + transition6、現行ブランチでは接近特徴量を足して
state20 + transition11）。docs には限界が明記されている:
「valueネットは明確な悪手の回避には効くが、**無目的な安全手同士の序列
（54手目9二香のような横並び）はまだ判別しない**」。

**仮説**: この横並び問題は**表現力の問題**であって、学習データや損失の問題ではない
可能性がある。数十個のスカラーに圧縮した時点で「9二香」と「他の安全手」の差が
消えている。HalfKP 的な位置 one-hot なら原理的に区別できる。

**なお HalfKPE9 の "E"（利き数）は、第1章の V1 そのもの**。
現状 `value_features.rs` の20次元には利き数が1つも入っていないので、
**NN 側も手作り項と同じ盲点を共有している**。V1 を実装したら、
同じ量を特徴量にも足すのが最も安い改善になる（次元がほとんど増えないので
過学習のリスクも小さい）。

**ただし直輸入は無理**: NNUE は億単位の教師局面で学習する。ついたては
1536局（≒10万局面級）。次元数を上げれば即座に過学習する
（docs/nn-value-phase1.md に同じ失敗の記録がある）。

**現実的な中間案**:
1. 玉相対の粗い位置特徴（玉からの距離ビン × 駒種）— HalfKP の圧縮版
2. 利き数を特徴に入れる（HalfKPE9 の E の部分）。E の差分計算と同時にやると安い
3. 段階的に次元を上げ、**そのつど 4シードで頑健性を確認**（既存手順）

優先度は中（長期）。E（利き差分）を先にやると 2 が安く手に入るので順序に意味がある。

### G. 不完全情報版 SEE

**やねうら王側**: `Position::see_ge()` — あるマスでの取り合いを**駒価値順に最後まで
シミュレート**して収支を返す。MovePicker が捕獲の良し悪しの判定に使う
（`movepick.cpp:341-350` のコメント参照）。

**ついたて側の現状**: `exchange_value` は交換1回ぶんの近似。
2手読み（`depth2_delta`, `strategy.rs:2568-`）が相手の応手を1手だけサンプルする。
`bin/analyze` は「只取られ」「損な交換」を誤り分類として数えている
= **実測で効いている弱点**。

**提案**: 粒子ごとに、着手先マスでの取り合い連鎖（SEE）を計算して加重平均する。
ただし**そのまま入れると間違える**:

> 将棋の SEE は「相手は必ず最善で取り返す」を仮定する。ついたてでは
> **相手はそこに駒があることを知らない**ので、取り返しは確率的にしか起きない。

`strategy.rs` は既に「露見度」の概念を持っている（`:491` の捕獲後残留露見リスク、
`:2606` の「捕獲通知でそのマスは相手に露見する」）。**SEE の各段の取り返しを
露見度で割り引く**のが正しい形。露見していないマスでの取り返しは起きにくい
＝ ついたて特有の「安全な突っ込み」が正しく評価される。

**罠**: これは `capture_bet_var_w`（捕獲賭け分散ペナルティ）と作用域が重なる。
同時に入れると二重計上になるので、**片方ずつアブレーションする**。

### H. データ生成の分布多様化（定跡ノブ）

**やねうら王側**: `book.cpp:1314-1384` の定跡オプション群。特に

- `BookIgnoreRate`（0-100）— **確率的に定跡を無視する**
- `BookMoves` / `BookDepthLimit` — 定跡を使う手数の上限
- `BookEvalDiff` — 最善手との評価値差がこれ以内の定跡手からランダムに選ぶ
- `script/engine_invoker5.py` の `--rand_book` — 対局スクリプト側で定跡順をシャッフル

**ついたて側の現状**: CLAUDE.md に明記された教訓
「**定跡（joseki.json）を更新したら学習データも再生成すること**」
＝ 定跡が凍結版（教師側）の序盤分布を決めてしまっているので、
定跡を変えると過去データが陳腐化する。

**提案**: 学習データ生成用のアリーナでだけ `BookIgnoreRate` 相当を入れる
（例: 20%の確率で定跡を使わない、定跡の使用手数をランダムに切る）。
序盤分布が定跡に固定されなくなるので、

- 定跡更新時のデータ再生成の必要性が下がる
- `from_home` 系の序盤感度が高い特徴量が、より広い分布で学習される

**罠**: 強さ検証用のアリーナには入れない（分散が増えるだけ）。
**データ生成用と検証用でノブを分ける**こと。

### history テーブル（ButterflyHistory / ContinuationHistory）

`history.h:195-266`。`[手番][from-to]` や `[駒][移動先]` に成功/失敗を蓄積し、
指し手オーダリングと reduction に使う。更新式（`history.h:91-125`）が上手く、
`entry += bonus - entry×|bonus|/D` で**上限 D を守りながら EMA 的に更新**する
（自然にゼロへ引き戻される）。この更新式自体は汎用的に有用。

**ただし**: ついたてで真っ先に思いつく応用「このマスで反則したことを覚えておく」は
**既に4通り試して全滅している**（メモリ: foul-economy-guide-attempts-2026-07-19。
occupies / path_blocks / prior_legal / 最終 p_legal 直接制約。すべて vs v7 で
51〜54%、有意差なし）。**この方向へは再挑戦しない**、が確定した判断。

適用するなら**別の用途**に限る:
「stage1 のスコア順位と、stage2 を通した後の順位のズレ」を局内で学習し、

### PUCT / MCTS の探索方策

`UctSearch.cpp:788-900`。`ucb = q + c × sqrt(n)/(1+n_i) × policy` に
FPU reduction（未訪問ノードの初期値を親の値から下げる）を組み合わせる。

ついたてで木は張れないが、**根の候補手への粒子予算の配分**は
まさに多腕バンディット問題なので、この式は使える（B の延長）。
`policy` に相当するのは stage1 のスコアを softmax したもの。

**ただし**: 現状は「全候補に均等」で、それを崩すと**評価の分散が候補間で不均一になる**。
スコア比較の公平性が壊れると、少数粒子でたまたま高く出た手が勝つ事故が起きる。
（`estimator` のソフト救済で `0.5^penalty` の重みを入れているのと同種の注意。）
導入するなら「**信頼区間の下限で選ぶ**（LCB）」など、分散を明示的に扱う形にすること。

## 4. 移植しないもの（理由つき）

| 技術 | 理由 |
|---|---|
| LMR / futility / razoring / ProbCut / null move | 探索木が前提。ついたては2手読みが上限で、深さ方向の reduction という概念が無い |
| aspiration window | αβ の窓の話。粒子加重平均には窓が無い |
| 置換表（局面キーでの共有） | 粒子ごとには作れるが、**同じ粒子が再訪される率が低い**（毎手作り直す）。`estimator` の指紋ユニーク化で既に主要な重複は潰れている |
| 千日手判定の優等局面（`is_repetition`） | 「同一盤面＋持ち駒が優越」の判定に**相手の盤面が必要**。粒子ごとには判定できるが、真の千日手はサーバーしか知らない |
| NUMA / スレッド分割 / large page | アリーナは既に CI のシャード並列。1手の思考は数百ms〜2秒で、スレッド化の複雑さに見合わない |
| SkillLevel（意図的な弱体化） | 用途が無い |
| USI プロトコル・定跡フォーマット | 接続先が Socket.IO の独自プロトコル。互換性の要求が無い |

## 5. 段取りの提案

依存関係と、既知のギャップへの効き方を考えると:

### まず評価関数から（費用対効果が良い順）

0. **V4（自玉8近傍の穴）を単独で先に**。既知情報だけ・粒子不要・実装が小さい。
   この1件で「新しい評価項を足して200局で測る」サイクルが回ることを確認してから
   重いものへ進む。~~合格条件は 200局で有意勝ち越し、または
   被詰めろオラクル（`bin/analyze`）の有意な改善~~

   **実施済み（2026-07-26、`king_hole_w` として既定0でmainへ）**。結果は
   「機構は確認できたが勝ちには変換されない」:

   | 指標（600局） | main 対照 | w=0.15 | w=0.4 |
   |---|---|---|---|
   | 被詰めろ | 363 | 339 | **300** |
   | うち打ち詰み | 276 | 208 | **186（−33%）** |
   | 実際に詰まされた | 75 | 69 | 72 |
   | vs v9 / v10 / v11 | 61.0 / 53.5 / 51.3 | 58.0 / 59.5 / 51.0 | 66.0 / 53.0 / 44.5 |

   被詰めろは w に**単調**で数σの改善（＝項は設計どおり動く）だが、
   `実際に詰まされた` は横ばいで勝率は非単調に散る。**相手botは自玉の位置を
   知らないので、与えた詰めろを実行できない**ため。

   **したがって上の合格条件（「または被詰めろの有意な改善」）は誤り**だった。
   被詰めろオラクルの改善が実害の減少に対応するのは**対人だけ**で、
   アリーナ（bot同士）では勝率に効かない。同じ構図が既に
   「en-prise 逃げは bot 相手だと実被害2.7%」で観測されている。
   **アリーナで採否を決める項の合格条件は勝率のみにすること。**
1. **V1（利き数）→ V3（予防的な紐）→ V2（距離重み）** の順。
   V1 は V3・V2 の前提（枚数がないと逓減も強弱も書けない）。
   V3 は自駒だけで計算できるので安く、V2 は全マス走査なので高い
   - V2 に入る前に **E（利きの差分計算）のコストを実測**する。
     素直に書くと `pressure_samples=16` の比ではないコストになる
2. V1〜V4 を入れたら、**同じ量を `value_features.rs` にも足す**。
   現状 NN の入力にも利き数が無いので、手作り項とNNの両方が同じ盲点を持っている。
   ただし NN 側は再学習（4シード・オフライン検証・w スイープ）が必要なので、
   手作り項の結果を見てから
3. V5（盤上駒の減価）・V6（玉の位置）は係数の符号すら未確定なので、
   SPSA の範囲を正負にまたがらせて探る。V7（方角別）は最後

### 次に探索・計算資源

4. **A → B → C を1セット**でやるのが最も筋が良い。
   A（時間配分）だけでは浮いた時間の使い道が無く、
   B（早期打ち切り）だけでは浮いた時間の貯め先が無く、
   C（widening）だけでは使える時間が増えない。3つで1つの機能になる。
   - 前提作業: `selfplay.rs:33-34` のフィッシャー定数を env で上書き可能にして、
     **本番相当（300秒+3秒）でアリーナを回せる**ようにする
   - 合格条件: 300+3 条件で v11 に 200局で有意勝ち越し。
     引き分け率・時間切れ・思考時間 p99 の悪化なし
   - C は improvement-plan 項目2（en-prise 逃げの足切り疑い）の**構造的な回答**に
     なっているので、逃げ手の選択率も併せて測る
2. **E（利き差分）は独立に効く**ので並行して良い。ただし着手前に実測でコストを確認する
3. **D は先に測る**（被詰めろオラクルで打ち以外の詰みの実害を数える）。
   実害が小さければ着手しない
4. **F は E の後**（利き数特徴が安く手に入る）
5. G / H は小粒。手が空いたときに

**共通の検証規律**（既存のものをそのまま適用）:
- 判定は CI の 200局ガントレット、`match_seed` ペア比較
- 主要シナリオ（kakutori / tokin-bet / gold-check / dragon-check-drop）の回帰確認
- `bin/analyze` の反則内訳・被詰めろ・只取られの悪化がないこと
